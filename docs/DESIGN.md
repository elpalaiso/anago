# anago — 내 도메인 + 내 서버 = 내 개인 네트워크

> 穴子(아나고, 붕장어): 구멍에 사는 장어. 터널에 사는 도구에게 이보다 맞는 이름이 없다.

## 1. 한 줄 요약

도메인과 서버(VPS)를 가진 사람이라면 누구나 10분 안에 자기 소유의
WireGuard 개인 네트워크를 갖게 해주는 단일 바이너리 셋업 도구.
certbot이 TLS에 해준 일을 개인 네트워크에 해준다.

## 2. 목표

- `anago server init --domain net.example.com` (VPS에서 1회) +
  `anago join net.example.com <코드>` (각 기기에서 1회) = 끝.
- 제3자 인프라 의존 0: 조율 서버도, 릴레이도, 인증도 전부 사용자의 서버.
  Tailscale이 회사여야 하는 이유(전 세계 릴레이망 운영)를 "인프라는 이미
  네 것"이라는 전제로 소거한다.
- 첫날부터 "항상 된다": 허브-스포크(서버 경유)가 기본 토폴로지라서
  NAT/CGNAT 환경(한국 LTE 포함)에서도 무조건 연결된다. 홀펀칭 직결은
  나중에 얹는 성능 최적화다.
- 오픈소스(MIT), 단일 바이너리, 낮은 서버 사양(1코어 VPS면 충분).

## 3. 비목표 (v1에서 의도적으로 안 만드는 것)

- **멀티 테넌시/조직 관리**: 사용자 1명(가족 규모까지)의 기기들. ACL,
  SSO, 감사 로그는 만들지 않는다.
- **모바일 클라이언트 앱**: iOS/Android는 공식 WireGuard 앱에 설정을
  내보내는(QR/파일) 것으로 해결한다. NetworkExtension의 늪에 들어가지
  않는다.
- **자체 암호화**: 암호 프리미티브는 한 줄도 직접 만들지 않는다.
  데이터 플레인은 WireGuard 그 자체다.
- **DERP류 글로벌 릴레이망**: 사용자의 서버가 곧 릴레이다. 릴레이를
  "운영"하는 문제는 이 설계에 존재하지 않는다.
- **범용 VPN**(전체 트래픽 라우팅/출구 노드): v1은 기기 간 사설망이다.
  exit node는 백로그.

## 4. 설계 원칙

1. **어려운 문제는 위임한다.** 암호화·터널=WireGuard(`wg`/커널),
   TLS=rustls+ACME, 프로세스 상주=systemd, DNS=Cloudflare API(또는 수동
   안내). anago가 직접 푸는 문제는 **조율(키·엔드포인트 교환)과 UX
   (셋업 마법사)** 둘뿐이다. — krill 원칙 1과 동일.
2. **서버는 데몬이 정당하다.** krill과 달리 anago server는 VPS에 상주하는
   것이 본질이다(조율+릴레이). 대신 클라이언트 쪽은 상주를 최소화한다
   (§6.3).
3. **단일 바이너리, 서버/클라 공용.** `anago` 하나가 서브커맨드로 양쪽
   역할을 다 한다. 배포물 1개, 문서 1벌.
4. **의존성은 마일스톤이 요구할 때만.** 코어 로직(설정 생성·상태 판정·
   프로토콜 타입)은 순수 std 라이브러리 크레이트(anago-core)로 분리해
   유닛 테스트를 깐다. tokio/axum/rustls는 바이너리 크레이트에만. —
   krill의 검증된 구조를 그대로 쓴다.

## 5. 아키텍처

```
                    net.example.com (A 레코드 → VPS)
                          │
        ┌─────────────────▼──────────────────┐
        │  VPS: anago server (상주)          │
        │  ├─ 컨트롤 API (HTTPS :443)        │  join/peers/endpoint 갱신
        │  ├─ ACME 인증서 자동 갱신          │
        │  └─ wg 허브 피어 (UDP :51820)      │  모든 기기의 트래픽 중계
        └───────▲──────────────▲─────────────┘
                │ wg 터널      │ wg 터널
         ┌──────┴─────┐  ┌─────┴──────┐
         │ 맥북       │  │ 데스크톱   │   ← anago join으로 등록된 기기
         │ 10.100.0.2 │  │ 10.100.0.3 │      (폰: wg 공식 앱 + 내보낸 설정)
         └────────────┘  └────────────┘
```

- **컨트롤 플레인**: HTTPS API. 기기 등록(join), 피어 목록 조회, 공개키
  교환. 상태의 원본은 서버의 단일 상태 파일(§9).
- **데이터 플레인**: WireGuard. M0~M1은 순수 허브-스포크 — 기기끼리의
  패킷은 서버를 경유한다(`AllowedIPs = 10.100.0.0/24`, 서버에서
  `ip_forward` + wg 라우팅). M2에서 홀펀칭 직결이 얹힌다.
- **주소 체계**: 사설 서브넷 기본 `10.100.0.0/24`(설정 가능). 서버 = .1,
  기기는 join 순서대로 할당.

**허브 경유의 신뢰 모델을 명시한다**: WireGuard는 피어 간 암호화이므로
허브-스포크에서 서버는 패킷을 복호화해 라우팅한다. 즉 서버는 트래픽을
볼 수 있다 — 그 서버가 **사용자 본인의 것**이라는 게 이 프로젝트의 전제
이고, 이것이 Tailscale(제3자 DERP는 E2E 유지 필요)과 위협 모델이 다른
이유다. M2 직결이 되면 기기 간 트래픽은 E2E가 된다. 문서에 정직하게
적는다.

## 6. 핵심 플로우

### 6.1 서버 초기화 (VPS에서 1회)

```
anago server init --domain net.example.com
```

1. wg 키쌍 생성, 서브넷/포트 결정, 상태 파일 생성.
2. DNS 확인: `net.example.com`이 이 서버의 공인 IP를 가리키는지 조회.
   - 아니면: **Cloudflare API 토큰이 있으면 A 레코드를 자동 생성**,
     없으면 "이 레코드를 추가하세요" 안내 후 재시도 대기. 토큰을 받는
     세 경로와 우선순위는 §8. (1차 provider = Cloudflare — 실검증 환경이
     Cloudflare 등록 도메인이다. 다른 provider는 수동 안내로 시작, API
     지원은 백로그.)
3. TLS 인증서 확보 — `--tls-cert/--tls-key`를 주면 그 경로를 쓰고,
   생략하면 ACME로 발급한다(§8의 선택 규칙). ACME 기본은 HTTP-01
   (:80 필요)이고 Cloudflare 토큰이 있으면 DNS-01이다(:80을 안 열어도
   된다). 갱신은 서버 데몬이 내장 처리하며, 손으로 부르는 길은
   `anago server renew`다(§8).
4. systemd 유닛 설치·기동(`/etc/systemd/system/anago.service`, ExecStart는
   `anago server run`). `--no-systemd`면 설치하지 않고 포그라운드로 실행할
   명령을 안내한다 — 컨테이너/비-systemd 환경.
5. 조인 코드 발급·출력: `anago join net.example.com 7QX4-M2KD`(형식은 §7.2).

#### `server init`의 순서와 "실패하면 아무것도 안 남는다"

M0의 약속은 **실패한 init이 파일을 남기지 않는다**였다. M1은 바깥을
건드리는 단계(A 레코드, CA)를 사이에 끼우지만 **약속은 그대로 간다.**

**공짜로 거절할 수 있는 것을 전부 먼저 한다.** 이미 허브인지, 플래그
조합이 말이 되는지, `wg`가 있는지, 그리고 **수동 인증서 쌍이 실제로
읽히는지**. 마지막 항목이 여기 있는 이유는 M0와 같다 — 그 파일은 지금
디스크에 있으므로 확인이 공짜이고, 뒤로 미루면 `--tls-cert` 오타 하나가
이미 남의 DNS를 고쳐 놓은 뒤에 드러난다. 이 단계들은 잠금 파일조차
만들지 않는다.

**그다음 잠금을 잡고, 바깥을 건드리기 전에 잡는다.** 마지막 publish만
감싸면 두 init이 나란히 ACME 계정을 등록하고 같은 `account.key`·인증서
쌍에 겹쳐 쓴다. publish에서 진 쪽의 파일이 남으면 이긴 쪽의 상태 파일이
가리키는 `account_url`과 디스크의 자격증명이 서로 다른 계정이 되고,
그 뒤 모든 갱신이 "다른 계정"으로 영구 거부된다(§9.1). 그래서 잠금은
**첫 외부 변경 전부터 마지막 파일까지** 잡고 있는다.

잠금 안에서 §6.1의 2·3번(A 레코드 → 인증서), 그리고 마지막으로 **이
기계를 허브로 만드는 파일들**. 상태 파일·wg 설정·(보관한다면) Cloudflare
토큰은 한 묶음으로 마지막에 쓰이고, 하나라도 실패하면 **그 호출이 실제로
만든 것만** 지운다. `create_new_private`가 이미 있는 파일을 절대 덮지
않으므로, 남의 파일은 애초에 그 목록에 들어오지 않는다.

**발급물도 같은 규칙을 따른다.** ACME는 상태 파일보다 먼저 세 파일
(`account.key`, `fullchain.pem`, `privkey.pem`)을 쓴다. 뒤에서 실패하면
그것도 되돌린다 — 남겨 봐야 **아무도 다시 찾아 쓰지 않기 때문이다.**
다음 `server init`은 디스크에 뭐가 있든 인증서를 새로 주문한다. 그러니
남기는 것은 레이트 리밋을 아껴 주지 않고, 허브도 아닌 기계에 개인키를
하나 놔두기만 한다 — 토큰을 상태 파일 시점까지 미루는 것과 같은
논리다(§7.1). 여기서도 **CA를 부르기 전에 무엇이 이미 있었는지 적어
두고, 이번 실행이 만든 것만** 지운다.

정리 가드는 **발급이 성공했을 때가 아니라 CA를 부르기 전에** 켠다.
발급은 계정 파일을 먼저 커밋하고 인증서 쌍을 그다음에 저장하므로(§9.1),
그 사이에서 실패하면 돌아오는 것은 오류뿐이고 "무엇을 썼는지" 말해 주는
결과가 없다. 성공을 신호로 켜는 가드는 정확히 그 경우 — 가장 정리가
필요한 경우 — 를 놓친다.

그래서 실패했을 때 보장되는 것: **아무것도 안 남고, 이 기계는 허브가
아니며, 같은 명령을 다시 돌리면 된다.**

일부러 되돌리지 **않는** 것은 하나뿐이다 — **A 레코드**. 바깥 세상의
변경이고, 사람이 손으로 넣었을 바로 그 레코드이며, 이 명령의 나머지가
끝났든 아니든 옳다. 나가는 길에 지우면 원래 되던 도메인을 망가뜨린다.
대신 **발급 뒤의 실패는 인증서가 한 장 소모됐다는 사실을 말한다** —
파일은 지웠지만 CA는 세었고, 한 도메인의 주당 허용량은 몇 장뿐이다.

**토큰은 상태 파일과 같은 시점에 쓴다.** 그래서 DNS-01 발급에는 토큰을
**파일이 아니라 인자로** 넘긴다 — init은 방금 A 레코드를 쓰면서 토큰과
zone을 이미 손에 쥐고 있고, zone은 id만이 아니라 통째로 넘긴다(전파
확인이 zone의 네임서버를 쓴다).

**zone은 A 레코드를 썼는지와 무관하게 기록한다.** DNS-01은 TXT로
답하므로 A 레코드가 아예 필요 없다. 공인 IP를 못 알아내 레코드를 못 쓴
허브도 인증서는 정상적으로 받고, 그 허브가 갱신하려면 zone과 토큰이
상태에 있어야 한다. 그래서 레코드를 안 썼을 때 비는 것은 **`record_id`
하나**이고 `zone_id`와 `token_path`는 그대로 적힌다.

**출력은 "한 것"과 "할 것"을 두 목록으로 나눈다.** M1이 M0의 수동 단계
둘 중 일부를 자동화하는데, "이건 됐다"와 "이건 네가 해야 한다"를 섞은
목록은 끝까지 읽히지 않는다. 앞 목록은 **보고**한다 — A 레코드 결과,
발급된 인증서와 만료·갱신 시점. 뒤 목록은 **번호를 매겨 요청**하고, 이미
일어난 일은 하나도 넣지 않는다. **보고할 것이 없으면 앞 목록은 통째로
사라진다** — 수동 인증서에 토큰 없는 허브(M0 그대로)는 M0의 출력을 그대로
받는다. 그게 실제로 일어난 일이기 때문이다.

**A 레코드를 anago가 썼으면 출력은 그걸 다시 시키지 않는다.** 이미 있는
레코드 옆에 사람이 하나 더 만들면 그게 §9.1이 손대기를 거부하는 라운드
로빈 상태다. 토큰이 없으면(또는 공인 IP를 알아내지 못해 레코드를 쓰지
않았으면) M0의 안내가 글자 그대로 나온다.

"할 것" 목록에 들어가는 것은 셋이다.

- **방화벽.** `api_port/tcp`와 `listen_port/udp`는 항상. **`80/tcp`는
  HTTP-01 허브에만** 나오고, "지금과 갱신할 때마다"라고 적는다 — 첫
  발급만 통과시키고 닫으면 몇 달 뒤에 갱신이 죽는다. DNS-01은 :80이
  필요 없고, 그게 DNS-01을 고르는 이유다.
- **프록시 확인.** zone을 조회한 허브(= 토큰이 있는 허브)에는 **A
  레코드가 DNS only인지 사람이 눈으로 보라고** 요청한다. §13이 말한
  대로 프록시가 켜져 있어도 인증서는 나오고 HTTPS도 되므로 **자동화가
  전부 초록인 채 터널만 죽는다** — anago가 볼 수 있는 것 중에 이걸
  드러내는 신호가 없어서, 사람에게 묻는 것 말고는 방법이 없다. 토큰이
  없으면 provider를 모르므로 Cloudflare를 지목하지 않고 DNS 단계에
  "프록시·CDN을 앞에 두지 말라"고 한 줄 붙인다.
- **수동 인증서.** `source = "manual"`이면 갱신은 사람 몫이다(§9.1).
  anago가 할 수 있는 것은 **언제 만료되는지 말해 주는 것**뿐이고, 그건
  "한 것"이 아니라 "할 것"이다.

**만료일은 인증서에서 읽는다.** §9.1이 정한 대로 바이너리가 PEM을 DER로
풀고 코어의 순수 함수가 `notAfter` 하나를 읽는다. 읽지 못하면 날짜를
지어내지 않고 "읽지 못했고 가정한 수명으로 갱신한다"고 말한다 — 갱신은
그대로 돌지만 사람은 자기가 가정 위에 있다는 것을 알 자격이 있다.
`manual` 인증서에도 채운다.

**문구는 코어(`render`)가 갖는다.** 인증서 한 줄과 스테이징 경고는
`server init`과 `server renew`가 같은 말을 해야 하므로 §8대로 한 곳에
둔다 — init이 자기 문구를 따로 들고 있으면 둘이 갈라진다.

### 6.2 기기 등록 (각 기기에서 1회)

```
anago join net.example.com 7QX4-M2KD
```

1. HTTPS로 서버에 코드 제출(코드는 1회용·만료 있음, §7).
2. 기기에서 wg 키쌍 생성 — **개인키는 기기를 떠나지 않는다.** 서버에는
   공개키만 등록. 응답으로 할당 IP·서버 공개키·엔드포인트 수신.
   (이 원칙의 유일한 예외가 아래 4번의 `--export`다 — §7.3.)
3. wg 설정 생성·적용(`wg-quick` 위임), 연결 확인(서버 .1에 ping).
4. `--export qr|conf`면 적용 대신 공식 WireGuard 앱용 설정 출력(폰 경로).

### 6.3 클라이언트 상주 문제

WireGuard 자체는 커널에 있으니 클라 데몬이 없어도 터널은 유지된다.
클라가 해야 할 일은 두 가지뿐이고 둘 다 가볍다:

- **keepalive**: wg의 `PersistentKeepalive = 25`로 NAT 매핑 유지 — 설정
  한 줄, 프로세스 0.
- **허브와의 대조**: 상주 데몬 대신 **systemd timer(맥은 launchd)로
  `anago sync`를 주기 실행**(기본 5분). M2의 홀펀칭이 들어오면 이 주기
  작업이 엔드포인트 갱신도 겸한다.

허브-스포크에서는 사실 동기화가 늦어도 통신은 된다(허브가 다 안다).
timer는 편의이지 정합성 요건이 아니다 — 이 성질 덕에 클라이언트도
사실상 데몬 0으로 굴러간다.

#### `sync`가 M1에서 실제로 하는 일

먼저 **하지 않는 일**부터. 기기가 새로 합류해도 **클라이언트 설정은
바뀌지 않는다.** `AllowedIPs = <subnet>` 한 줄이 서브넷 전체를 터널로
보내고 라우팅은 허브가 하므로, 피어가 둘이든 열이든 `anago.conf`는 같다.
M0가 `sync` 없이도 도는 이유가 이것이고 M1에도 그대로다. **"피어 목록을
당겨 설정을 갱신한다"는 M1에서 거의 언제나 "갱신할 것이 없다"로
끝난다** — 그렇게 끝나는 것이 정상이다.

그런데도 sync를 두는 이유는 셋이다.

1. **이 기기가 아직 등록돼 있는지 확인한다.** 허브에서 `anago rm`으로
   지워졌다면 토큰이 그 즉시 죽어(§7.1) 호출이 401로 돌아온다. 이것을
   알려 주는 것이 없으면 기기는 죽은 터널을 붙들고 "왜 안 되지"만
   반복한다.
2. **허브에 살아 있음을 알린다.** 인증된 호출이 `last_seen`(§9.1)을
   갱신하고, 그래야 허브의 `anago ls`가 어느 기기가 살아 있는지 말할 수
   있다.
3. **로컬 설정이 허브와 여전히 맞는지 대조한다.** 이것이 유일하게
   "동기화"라는 이름값을 하는 일이다.

**3번을 하려면 비교 대상이 필요하다.** 그래서 `GET /api/v1/peers` 응답에
**허브 자신에 대한 값을 M1에서 더한다.** 이것 없이는 sync가 "설정이
맞다"고 말할 근거가 없고, 근거 없이 맞다고 하는 것은 확인이 아니라
가정이다.

무엇을 담는지는 한 줄로 정한다: **`device.json`이 허브에 대해 담고 있는
값 전부**(§9.2)다. 그래야 대조에 빠지는 값이 없고, 나중에 "왜 저건
없지"를 다시 논할 일도 없다. 이름은 `JoinResponse`가 쓰는 것을 **글자
그대로** 쓴다 — 같은 값을 다른 이름으로 두 번 정의하지 않는다:

```json
{
  "peers": [
    { "name": "macbook", "public_key": "<wg base64>", "address": "10.100.0.2" }
  ],
  "subnet": "10.100.0.0/24",
  "server_public_key": "<wg base64>",
  "server_endpoint": "net.example.com:51820",
  "server_address": "10.100.0.1"
}
```

**중첩하지 않고 최상위에 평평하게 둔다.** 이유는 둘이다. (1) 이 이름들이
`JoinResponse`의 최상위 이름과 같아야 디코더 한 벌이 양쪽을 읽는다.
(2) `server`라는 키는 이미 상태 파일에서 **다른 뜻**(개인키·공개키·주소,
§9.1)으로 쓰이고 있어, 같은 이름에 다른 내용을 담으면 읽는 사람이 헷갈린다.

스키마 원본은 anago-core의 타입이므로(§8) 타입 쪽 모양도 못박는다:
`PeersResponse`는 `peers`와 **`Option<허브 정보>`** 를 갖고, 그 옵션 하나가
위 네 키에 대응한다. 즉 **네 필드는 함께 있거나 함께 없다. 일부만 있는
응답은 디코드 에러다** — 반쯤 믿을 수 있는 응답을 반쯤 믿지 않는다.

**M1 클라이언트가 M0 허브에 붙으면** 네 필드가 통째로 없다. 그때 sync는
**대조(3번)를 건너뛰고 1·2번만 하고 정상 종료한다(코드 0).** 없는 것을
"다르다"로 읽으면 5분마다 설정을 다시 쓰는 무한 재작성이 된다. 사람이
직접 쳤을 때는 "이 허브는 대조를 지원하지 않는다"고 한 줄 말하고,
`--quiet`면 침묵한다.

반대 방향(M0 클라이언트가 M1 허브에 붙는 경우)은 그냥 된다 — 응답
디코더가 아는 필드만 읽고 모르는 필드는 무시하기 때문이다.

덧붙여, 이 추가는 §9.1이 `endpoint`를 M2까지 미룬 것과 다른 종류다.
그건 기기가 **보고하는** 새 쓰기 경로이고 의미를 새로 정해야 하는 값이다.
이쪽은 허브가 이미 join 때 알려 준 값을 다시 말해 주는 것뿐이다.

대조 결과와 행동은 이렇게 고정한다:

| 허브가 말한 것과 로컬이 | sync가 하는 일 |
|---|---|
| 전부 같다 | 아무것도 하지 않는다 — M1의 거의 모든 경우 |
| 피어가 늘거나 줄었다(나 말고) | 아무것도 하지 않는다. 설정에 영향이 없다 |
| 서버 공개키 또는 엔드포인트가 다르다 | wg 설정을 다시 쓰고 `wg syncconf`로 적용, `device.json`도 갱신 |
| 401 | **고치지 않는다.** 제거됐다고 말하고 정리 절차를 안내 |
| 목록에 내 이름·주소가 없다 | **고치지 않는다.** 재가입을 안내 |
| 서브넷이 다르다 | **고치지 않는다.** 허브가 다시 세워졌다는 뜻이므로 재가입을 안내 |

**sync는 파괴적인 일을 스스로 하지 않는다.** 401을 받았다고
`wg-quick down`을 하거나 `device.json`을 지우지 않는다. 허브가 잠시
잘못된 상태일 수도 있고(복원 중인 백업), 무엇보다 5분마다 도는 무인
작업이 사람의 터널을 내리는 것은 비율이 맞지 않는다. 말하고 멈춘다.

**대신 정리 절차를 정확히 안내한다.** "기기 파일을 지우세요"는 명사이지
할 수 있는 일이 아니다 — 이 기계의 두 경로를 그대로 적고, 절차 전체를
적는다(wg 설정이 남아 있으면 join이 네트워크에 닿기도 전에 거부되고,
터널은 아직 올라와 있을 가능성이 높다). 401뿐 아니라 **모든 detachment**
(목록에서 사라짐·주소 재배정·서브넷 변경)가 같은 안내를 달고 나오며,
`--quiet`에서도 나온다 — 이 한 줄이 타이머가 존재하는 이유다.
**말 그대로 한 줄이다**: 저널은 엔트리 단위로 보이므로 이유와 절차를 두
줄로 나누면 사람이 한쪽만 읽는다. 위 표의 "stderr 한 줄"이 그 뜻이다.

이 문구는 **`render`에 한 벌만 둔다**(§8). 같은 절차를 말해야 하는 곳이
셋이다 — sync의 detachment(401 포함), `ls`·`rm`의 401. 셋이 각자 쓰면
그중 하나가 단계를 빠뜨리는 식으로 갈라진다. 코어의 `Detachment`는
**이유만** 말하고, 두 경로를 아는 호출자가 절차를 붙인다. `join`의 "이미
가입함"은 일부러 이것이 아니다 — 거기선 제거된 것이 없으므로 끝이 새 코드가
아니라 허브의 `anago rm`이다.

#### 적용 순서 — 실패하면 반드시 다시 시도되게

위 표의 셋째 줄(서버 공개키·엔드포인트가 다르다)만이 실제로 무언가를
쓰는 경로다. 순서를 못박는다.

0. **`device.json`은 이번 실행이 읽은 그 파일에 되쓴다.** `--config`가
   가리킨 경로가 있으면 그 경로다 — §9 규칙으로 다시 풀면 타이머(root,
   세션 밖)는 엉뚱한 파일을 쓴다.
1. 기존 `/etc/wireguard/anago.conf`에서 **이 기기의 개인키를 읽는다.**
   개인키는 그 파일에만 있고 어디에도 사본이 없다(§9). 파일이 없거나
   `PrivateKey`를 읽을 수 없으면 **고치지 않고 재가입을 안내한다** —
   설정을 다시 만들 재료가 없다.
2. 새 설정 텍스트를 만들어 `anago.conf`에 원자적으로 쓴다.
3. `wg syncconf`로 적용한다.
4. **적용에 성공했을 때만** `device.json`을 새 값으로 쓴다.

**4번이 3번 뒤에 있는 것이 이 절의 요점이다.** `device.json`은 "허브와
맞춰 놓은 마지막 상태"라는 뜻이고, 적용이 실패했는데 먼저 커밋하면 다음
sync가 로컬과 허브를 같다고 판정해 **다시 시도하지 않는다.** 그러면
커널에서 도는 설정만 영영 낡은 채로 남고, 증상은 "닿기는 하는데 터널이
안 산다"인데 아무도 그 사실을 말하지 않는다. 순서를 뒤집어 두면 실패한
다음 실행이 같은 불일치를 다시 보고 다시 시도한다 — **재시도가 조건이
아니라 구조로 보장된다.**

`wg syncconf`는 파일 이름을 받으므로 `wg-quick strip`의 결과를 잠깐
디스크에 둔다. 그 파일에도 **같은 개인키가 들어 있으므로** 실패 경로를
포함해 모든 길에서 지운다(§7.1). 원본 옆에 0600으로 만든다 — 그 디렉터리는
이미 root 전용이고, 다른 파일시스템으로 넘어갈 이유가 없다.

2번까지만 되고 3번이 실패한 상태는 안전하다. 파일에는 새 설정, 커널에는
옛 설정, `device.json`에는 옛 값이 남는데, 다음 sync가 같은 텍스트를 다시
쓰고(멱등) `syncconf`를 다시 부른다. 재부팅으로 `wg-quick up`이 돌면 그
파일이 그대로 올라가 저절로 맞는다.

커널 상태를 `wg show`로 읽어 비교하는 방법도 있지만 택하지 않는다.
커밋 순서 규칙이면 **판정의 입력이 파일 둘(`device.json`,
허브 응답)로 유지되어** 코어의 순수 함수로 전부 테스트되는데, 커널을
읽기 시작하면 그 판정이 실행 환경에 의존하게 된다(§4 원칙 4).

M1에서 서버 공개키·엔드포인트가 실제로 바뀔 일은 드물다 — 둘 다
`server init`이 한 번 정하고, 두 번째 `init`은 거부된다(§8). 그래도 이
비교가 값을 하는 경우가 있다: 허브를 부분 복원했거나(`state.json`은 옛
것, wg 키는 새로 만든 것) 사람이 `/etc/wireguard/anago.conf`를 손댄
경우다. 그때 증상은 "허브에는 닿는데 터널만 죽어 있다"이고(§13이 걱정
하는 바로 그 모양), 이 대조가 없으면 아무도 그 사실을 말해 주지 않는다.

#### 주기와 실패 규약

**기본 주기는 5분이다.** 짧게 잡을 이유가 없다: 위 표대로 대부분의
변화는 클라이언트에 아무 일도 시키지 않고, 제거된 기기의 트래픽은 허브가
피어를 지우는 **그 순간** 끊기므로 sync가 늦는 것은 *통신*이 아니라
*안내*가 늦는 것뿐이다. 길게 잡지 않는 이유는 M2에서 엔드포인트 갱신이
이 작업에 얹히기 때문이다. `--interval`로 바꿀 수 있다(§8).

**허브에 닿지 못하는 것은 실패가 아니다.** 노트북은 대개 네트워크 밖에
있고 그것이 정상이다 — §6.3의 성질대로 동기화가 늦어도 통신에는 지장이
없다. 그래서 실패를 두 종류로 나눈다.

| 상황 | 종료 코드 | `--quiet`일 때 |
|---|---|---|
| 변경 없음 / 적용 성공 | 0 | 아무 말도 하지 않는다 |
| 허브에 닿지 못함(DNS·연결 거부·타임아웃) | 0 | 침묵 |
| 이미 다른 sync가 도는 중(잠금) | 0 | 침묵 |
| 401 — 이 기기가 제거됨 | ≠0 | stderr 한 줄 |
| `device.json`이 없거나 깨짐 | ≠0 | stderr 한 줄 |
| TLS 검증 실패 | ≠0 | stderr 한 줄 |
| wg 설정은 썼는데 적용(`syncconf`)이 실패 | ≠0 | stderr 한 줄 |

윗줄 셋을 0으로 두는 이유는 저널 때문이다. 종료 코드가 0이 아니면
systemd는 유닛을 실패로 기록하고, 카페 와이파이에 있었다는 이유로 하루에
수백 줄이 쌓이면 정작 봐야 할 401이 그 안에 묻힌다. **조용히 넘길 수
있는 것과 사람이 손대야 하는 것을 종료 코드로 가른다.**

**윗줄의 "못 닿음"은 닫힌 목록이다** — DNS·연결 거부·타임아웃, 그리고
연결 도중 끊김. 저절로 없어지는 것들이라 침묵이 맞다. 나머지 전송 오류는
전부 아랫줄이다: `device.json`의 도메인이 호스트명이 아니거나 토큰을
헤더에 담을 수 없는 것은 **사람이 파일을 고쳐야 하는 일**이고, HTTP가
아닌 응답이나 감당 못 할 크기의 응답은 **중간에 뭔가 끼어 있다는 뜻**이라
5분 뒤에 다시 봐도 같다. 이것들을 "못 닿음"으로 묶으면 타이머가 영영
삼킨다.

TLS 검증 실패는 네트워크 문제가 아니라 신뢰 문제라 아랫줄에 둔다.
캡티브 포털이 가로챈 것이 흔한 원인이므로 메시지가 그 가능성을 먼저
말하지만, 조용히 삼키지는 않는다 — 진짜 중간자도 같은 모양이다.

**허브의 답을 root 설정의 컴파일러로 신뢰하지 않는다.** TLS는 그 답이
허브에서 왔다는 것만 말하지 허브가 멀쩡하다는 것은 말하지 않는다 —
복원 중인 백업일 수도, 버그일 수도, 남이 쥔 허브일 수도 있다. 그런데
`server_public_key`·`server_endpoint`는 곧장 root 소유 `wg-quick` 파일로
렌더링되고, 그 형식은 **지시문 목록**이다. 유효한 엔드포인트 뒤에 줄바꿈과
`PostUp = …`을 붙이면 재부팅 때 root가 그 명령을 실행한다. 게다가
`wg-quick strip`이 `PostUp`을 떼고 넘기므로 `syncconf`는 성공하고 파일과
`device.json`이 그대로 커밋된다. 그래서 **join이 검사하는 것과 똑같이**
(`wg::parse_key`, `checked_endpoint`, 주소·서브넷 파싱) 응답을 검사하고,
하나라도 어긋나면 **아무 파일도 건드리지 않고 멈춘다**(§7). 검사는 응답을
받은 자리에서 한 번 하고, 그 뒤로는 **검사를 통과한 값만** 비교·설정·
`device.json`에 흘러간다 — 원문 문자열이 파일까지 가는 경로를 남기지
않는다.

**sync는 root로 돌면서 사람의 파일을 만진다.** 그래서 `join`과 같은 규칙을
따른다(§13). `device.json`이 있는 디렉터리를 **한 번 열어 그 핸들로**
읽기·잠금·되쓰기를 전부 한다 — 경로로 확인하고 경로로 다시 쓰면 그 사이에
부모 디렉터리를 rename하고 심볼릭 링크를 갖다 놓는 경합을 그 경로의 주인이
이긴다. 그리고 **되쓸 때 원래 소유자에게 돌려준다**: 그냥 쓰면 임시 파일이
root 소유로 만들어져 rename되고, 서버 값이 한 번이라도 바뀐 뒤부터 0600
`device.json`이 root의 것이 되어 §9가 약속한 "평범한 사용자 셸의
`anago ls`·`rm`"이 읽지 못한다. 소유자는 환경변수로 추측하지 않고 **그
파일에서 읽는다** — 타이머에는 `SUDO_UID`가 없고, 파일은 바로 거기 있다.

**두 실행이 겹치지 않게 잠근다.** 타이머가 도는 중에 사람이 손으로 치는
것은 이상한 일이 아니고, 겹치면 둘이 **서로 다른 응답으로** 같은
`anago.conf`와 같은 `device.json`을 다시 쓴다 — `wg syncconf`에 넘기는
임시 파일 이름도 하나라 한쪽이 다른 쪽이 읽으려던 파일을 지울 수 있다.
잠금은 **이번 실행이 읽은 `device.json` 옆**(`sync.lock`)에 둔다. wg 설정
옆이 아닌 이유는 그 디렉터리는 방금 읽은 곳이라 반드시 있고, `device.json`은
있는데 `/etc/wireguard`가 아직 없는 기기도 "맞다"고 보고할 수는 있어야
하기 때문이다. **기다리지 않고 시도만** 한다 — 이미 도는 실행이 이 실행이
할 일을 하고 있으므로, 진 쪽은 위 표대로 조용히 0으로 끝난다.

**`--quiet`는 성공한 판정만이 아니라 실패에도 걸린다.** 위 표의 윗줄
셋(변경 없음·못 닿음·잠금)은 전부 침묵이다. 실패라고 해서 새어 나가면
다른 데 있던 노트북이 5분마다 한 줄씩 쌓고, 그게 정확히 이 표가 막으려던
소음이다.

**재시도도 백오프도 하지 않는다.** 5분 뒤에 타이머가 다시 부르고, 그
5분이 곧 백오프다. 한 번의 실행 안에서 재시도하면 실패가 겹칠 때 호출이
배로 늘 뿐이다.

## 7. 보안 모델

- **전송**: 컨트롤 API는 TLS(ACME 정식 인증서, 자가서명 없음). 데이터
  플레인은 WireGuard(Noise).
- **조인 코드**: 1회용, 기본 15분 만료, 서버에서 `anago code`로 재발급.
  코드 = 등록 권한 그 자체이므로 짧게 살고 즉시 죽는다. 형식은 §7.2.
- **키**: wg 개인키는 각 기기 로컬에만(0600). 서버 상태 파일에는 기기의
  공개키·IP·이름과 토큰 해시(§7.1)만 — 기기 개인키도, 토큰 평문도 서버에
  없다. **예외는 `join --export` 하나이고, 그 경계와 대가는 §7.3이
  따로 다룬다.** 기기 제거 = `anago rm <이름>` → 서버가 피어에서 제거, 다음 sync
  때 각 기기 설정에서도 사라진다.
- **API 인증**: join 이후의 호출(`ls`/`rm`, M1의 `sync`)은 join 때
  발급되는 기기 토큰(bearer)으로. 토큰은 기기 로컬 저장(0600), 서버에는
  해시만 — 상세는 §7.1.
- **Cloudflare 토큰**: 필요한 최소 권한만 가진 스코프 토큰을 요구하도록
  문서화한다. 그 최소가 **둘**이라는 점을 분명히 한다 — 해당 존에
  **Zone → DNS → Edit**(레코드를 쓴다)와 **Zone → Zone → Read**(도메인이
  사는 존을 찾는다). 존 조회가 먼저 일어나므로 편집 권한만 준 토큰은
  검증은 통과하고 첫 조회에서 403이 나며, 안내가 편집 권한만 말하면
  사람은 이미 가진 권한을 다시 주고 같은 벽을 만난다. `server init`
  완료 후엔 인증서 갱신(DNS-01일 때)에만 쓰므로, **그때만** 상태 파일이
  아닌 별도 파일(0600)에 남긴다 — 저장 위치와 이유는 §9.1.

### 7.1 기기 토큰 — M0 확정: 해시 저장

**서버는 기기 토큰을 SHA-256 해시(hex 64자)로만 저장한다. 평문은 상태
파일에도 로그에도 남기지 않는다.**

- **형식**: 256비트 랜덤을 hex로 쓴 64자 `[0-9a-f]`. 조인 코드와 달리
  사람이 손으로 옮겨 적지 않고 설정 파일에 저장되므로, 읽기 좋은
  charset보다 모호함 없는 인코딩이 낫다 — hex면 바이너리가 랜덤
  32바이트를 그대로 인코딩하면 되고 거부 샘플링이 필요 없다.
- **생성**: 바이너리가 `/dev/urandom`에서 32바이트를 읽어 만든다(순수
  std로 가능, 별도 크레이트 없음). 읽기에 실패하면 약한 난수로
  폴백하지 않고 join을 실패시킨다.
- **저장**: 서버는 `peers[].token_hash`(§9.1)에 해시만. 클라이언트는
  `~/.config/anago/device.json`에 평문을 0600으로 — 매 요청에 제시해야
  하므로 불가피하다.
- **검증**: 클라가 bearer로 평문을 보내면 서버가 `sha2`의 SHA-256으로
  해싱해 저장된 해시와 상수시간 비교한다.
- **폐기**: `anago rm <이름>`으로 피어를 지우면 그 토큰은 그 즉시
  무효다. 회전·갱신 API는 M0에 없다 — 필요하면 기기를 다시 join한다.

**왜 평문 저장이 아니라 해시인가.** 상태 파일에는 어차피 서버 wg
개인키가 들어 있으니 "파일이 새면 어차피 끝"이라는 반론이 가능하다.
그래도 해시를 고른 이유는 셋이다. (1) 개인키는 파일에 있을 수밖에
없지만 토큰 평문은 **없앨 수 있는 비밀**이다 — 없앨 수 있는 건 없앤다.
(2) 상태 파일이 통째로 유출되는 경로(백업, 이슈에 붙여넣은 덤프,
`server status` 출력 실수)는 서버 침해와 달리 흔하고, 그때 평문 토큰은
곧바로 재사용 가능한 자격증명이다. (3) 비용이 크레이트 하나다 —
바이너리 크레이트가 `sha2`를 **직접 의존성으로** 선언해 쓴다. rustls가
어떤 provider를 끌고 오든 그건 전이 의존성이라 우리 코드가 직접 부를 수
없고, rustls가 범용 SHA-256 API를 보장하지도 않는다. 그러니 "이미 있는
걸 재활용"이라는 절약은 성립하지 않는다 — 의존성 하나를 명시적으로
추가하는 쪽이 정직하고, 구현 단계에서 다시 고를 일도 없다. anago가
SHA-256을 직접 구현하는 일은 없다(§3, §4 원칙 1).

**솔트·KDF를 쓰지 않는 이유**: 토큰은 사람이 고른 비밀번호가 아니라
256비트 균일 랜덤이다. 사전 공격·레인보우 테이블의 대상이 아니므로
argon2/bcrypt는 비용만 늘리고, 단일 SHA-256으로 충분하다. 이 성질이
깨지는 순간(예: 사람이 고른 토큰 허용)엔 이 문단을 먼저 고친다.

**anago-core의 책임 경계**: 코어는 순수 std라 해싱을 하지 않는다.
코어가 갖는 것은 (a) 토큰 **형식 검증**(길이 64, hex 문자만)과
(b) 두 해시 문자열의 **상수시간 비교**(길이 확인 후 XOR 누적 —
암호 프리미티브를 만드는 게 아니라 조기 반환을 없앤 비교일 뿐이다)
둘뿐이다. 해싱은 바이너리 크레이트가 `sha2`에 위임한다. 즉
토큰의 규칙은 코어에서 유닛 테스트되고, 계산은 라이브러리에 맡긴다.

### 7.2 조인 코드 형식

**`XXXX-XXXX` — 하이픈으로 끊은 4자 두 묶음, 총 8자.** 사용할 문자는
`23456789ABCDEFGHJKMNPQRSTVWXYZ` 30자다.

- **혼동 문자 제외**: `0`/`O`, `1`/`I`/`L`, `U`(V와 혼동)를 뺐다. 이
  코드는 VPS 터미널에서 눈으로 읽어 노트북·폰에 손으로 옮기는 문자열
  이라, 알파벳 크기를 32에서 30으로 줄여 잃는 비트(0.1비트/자)보다
  잘못 읽어 실패하는 비용이 크다.
- **엔트로피**: 30^8 ≈ 6.6×10^11, 약 39.3비트. 15분 만료·1회용과
  합치면 초당 100회로 두들겨도 15분 창에서 성공 확률이 10^-7 수준이다.
  M0에는 레이트 리밋이 없으므로(백로그) 안전 마진을 엔트로피가 진다.
  이전 초안이 쓰던 `CODE-XXXX`는 자리표시자였고, 실제 형식은 이 절이
  정본이다.
- **입력 관용**: 서버가 출력하는 정규형은 대문자에 하이픈 하나
  (`7QX4-M2KD`). 검증은 대소문자를 가리지 않고, 하이픈과 공백은
  무시한다 — `7qx4m2kd`도 같은 코드다. 사람이 옮겨 적는 문자열에서
  대소문자 실수로 등록을 막을 이유가 없다.
- **책임 경계**: 난수는 바이너리가 만든다(토큰과 같은 `/dev/urandom`,
  §7.1). anago-core는 알파벳·형식·정규화·검증만 갖는다 — 순수 함수라
  유닛 테스트로 고정된다.

### 7.3 `--export` — 개인키가 기기를 떠나는 유일한 경로

`anago join --export qr|conf`(§8)는 **§6.2의 "개인키는 기기를 떠나지
않는다"가 성립하지 않는 단 하나의 경로**다. 폰의 wg 개인키가 폰이 아니라
이 노트북에서 만들어져, 터미널 화면이나 파일을 거쳐 폰으로 건너간다.
원칙에 예외를 두는 것이니 왜 그런지, 무엇이 노출되는지, 무엇으로 막는지를
여기에 적는다.

**왜 이렇게 하는가.** 폰에는 anago 바이너리가 없다 — 모바일 앱을 만들지
않는 것이 §3의 비목표다. 그래서 폰은 조인 코드를 제출할 수도, 컨트롤
API를 부를 수도 없다. 누군가는 폰을 대신해 등록해야 하고, 등록에는 폰의
공개키가 필요하다. 키를 누가 만드느냐가 갈림길이다.

**더 엄격한 대안이 있다는 것도 적어 둔다.** 공식 wg 앱은 앱 안에서 키를
만들고 공개키를 보여 줄 수 있다. 그 44자를 사람이 노트북으로 옮기고
`anago join --public-key <pk> --name 폰` 같은 표면으로 등록하면 **개인키는
폰을 떠나지 않는다.** 이 길을 M1에 넣지 않는 이유는 옮겨 적는 문자열의
길이다 — 조인 코드를 8자로 줄이려고 §7.2에서 알파벳까지 깎았는데, 같은
문서가 44자 base64를 손으로 옮기라고 할 수는 없다. 대신 **백로그에
남긴다**: 위협 모델이 노트북 터미널을 믿지 못하는 사람에게는 이쪽이
맞는 답이고, QR로 폰→노트북 방향을 읽을 수 있게 되면 옮겨 적기 문제도
사라진다.

**무엇이 어디로 새는가.** 출력물은 폰의 개인키를 평문으로 담은 wg 설정
이다. 경로별로 남는 자리가 다르다.

- **`--export qr`**: 터미널의 **스크롤백**에 남는다. `clear`로는 지워지지
  않고, 터미널 에뮬레이터에 따라 스크롤백이 **디스크에 저장**된다.
  원격 세션이면 SSH를 타고 지나가 중간 서버의 tmux 스크롤백에도 남는다.
  화면 캡처와 어깨너머도 QR 쪽이 더 쉽다 — 사람이 일부러 폰 카메라를
  들이대는 그림이라서 그렇다.
- **`--export conf`**: 표준출력이면 위와 같고, `--out`으로 파일에 쓰면
  파일시스템에 남는다. 백업과 클라우드 동기화 폴더가 진짜 위험이다 —
  `~/Documents`나 `~/Desktop`에 떨어진 `.conf` 하나가 조용히 어딘가로
  복제된다.

**그래서 정하는 규칙.**

- **출력 채널은 `--out`의 유무로 갈린다.**
  - `--out`이 없으면 **본문은 표준출력**으로, 경고·안내는 **stderr**로
    나간다. 파이프로 넘길 때 경고가 섞이면 그 설정이 곧바로 깨지기
    때문이다.
  - `--out`이 있으면 **본문은 그 파일로만** 간다. 표준출력에는 아무것도
    나가지 않고, 경고·안내는 그대로 stderr다.
- **anago가 만드는 파일은 0600이다.** `--out`은 `O_CREAT|O_EXCL`로,
  모드 0600으로 연다 — **이미 있는 파일은 덮어쓰지 않고 에러**이고
  (실수로 남의 프로필을 지우지 않는다), umask는 비트를 빼기만 하므로
  0600보다 느슨해질 수 없다.
- **셸 리디렉션은 anago가 지켜 줄 수 없다.** `--export conf > phone.conf`
  로 만들어진 파일의 모드는 anago가 아니라 셸의 umask가 정하고, 흔한
  umask에서는 **0644**가 된다. 그래서 이 절의 규약을 정직한 범위로
  쓴다: "conf 파일은 0600"이 아니라 **"anago가 만드는 파일은 0600"**
  이다. 파일이 필요하면 `>`가 아니라 `--out`을 쓰라는 경고를 **감지 없이
  항상** stderr 배너에 넣는다 — 표준출력이 파일인지 들여다보고 말을
  바꾸는 것보다 언제나 같은 문장을 말하는 편이 예측 가능하고, `| ssh`
  같은 정당한 파이프를 막지도 않는다.
- **anago는 그 파일을 자동으로 지우지 않는다.** 폰이 읽기 전에 사라지면
  곤란하다. 대신 출력이 지우는 명령을 그대로 알려 준다.
- 경고에 담기는 것: 이 텍스트는 폰의 개인키라는 것, 옮긴 뒤 지워야 한다는
  것, QR이면 스크롤백까지 지워야 한다는 것, 그리고 위의 `>` 대신 `--out`.
  스크롤백 지우기는 터미널마다 다르므로 명령 하나를 단정하지 않고 방법을
  안내한다.

**렌더링된 설정 텍스트에는 타입 경계를 둔다.**

`PrivateKey`(§9.1 상태의 키 필드)가 막아 주는 것은 **렌더링 전 구조체**의
우발적 `{:?}`뿐이다. 일단 wg 설정으로 렌더링되고 나면 그것은 개인키가
박힌 평범한 `String`이라, 에러에 붙이거나 디버그로 찍는 순간 그대로 샌다
— 타입은 거기까지 따라오지 않는다. 그러니 "로그에 넣지 않는다"를 규칙만으로
두지 않고 경계를 하나 더 둔다.

- 코어의 wg 설정 생성 함수들(`server_config`, `client_config`,
  `--export`용 프로필)은 `String`이 아니라 **`SecretText`**를 돌려준다.
  내보내기용이든 로컬 `anago.conf`용이든 개인키가 든 텍스트는 같은
  타입이다 — 서버 설정에는 허브의 개인키가 들어 있어 사정이 똑같다.
- `SecretText`는 **`Debug`와 `Display` 둘 다** 내용 대신
  `SecretText(redacted)`를 낸다. `PrivateKey`가 이미 쓰는 패턴을 한 단계
  위에 그대로 적용한 것이고, 같은 방식으로 유닛 테스트에 고정된다.
- 실제 바이트를 얻는 길은 **`expose()` 하나뿐**이다. 그래서 비밀이
  프로세스 밖으로 나가는 자리가 소스에서 grep 하나로 세어진다 — 파일에
  쓰기, 표준출력에 쓰기, QR 인코더에 넘기기, 그 셋뿐이어야 한다.
- **에러 타입은 본문을 담지 않는다. 경로와 원인만 담는다.** 이건 타입이
  강제하지 못하는 규칙이라 리뷰에서 지키는 항목으로 남긴다 —
  `SecretText`는 실수를 어렵게 만들 뿐 불가능하게 만들지는 않는다.

**노출의 크기와 복구.** 이 출력이 새면 새는 것은 **그 폰의 터널 접속
권한**이다. 폰 프로필에는 기기 토큰이 들어가지 않으므로(§8) 컨트롤 API
권한은 함께 새지 않는다 — `ls`도 `rm`도 못 한다. 그리고 복구는 한 번이면
된다: 허브에서 `anago rm <이름>`을 하면 그 공개키가 피어에서 사라지고
유출된 개인키는 그 즉시 쓸모없어진다. 같은 이름으로 다시 내보내려면
먼저 지워야 한다(이름 중복은 서버가 막는다, §8.1).

**가정을 분명히 한다.** 이 경로의 안전은 "이 기기와 이 터미널을
신뢰한다"는 가정 위에 선다. 공유 장비나 녹화되는 세션에서는 그 가정이
서지 않고, 그때는 `--export`를 쓰지 않는 것이 맞는 답이다.

## 8. 인터페이스 스펙 (CLI)

각 줄에 도입 마일스톤을 붙인다. **바이너리는 자기 마일스톤까지의 표면만
구현하고, 그 뒤의 서브커맨드·플래그에는 "아직 없음"이라고 답한다 — 그
문구에는 그 명령이 실제로 들어오는 마일스톤을 넣는다.** M0 바이너리에서
`anago sync`를 치면 "M1에서 들어옴", `anago ping`이면 "M3에서 들어옴"
이다. 마일스톤을 한 값으로 고정하면 "언제 쓸 수 있나"라는 정작 궁금한
것에 답하지 못한다 — 있는 척하는 no-op보다야 낫지만 안내로서는
반쪽이다.

M0 표면(구현 완료):

```
anago server init --domain <d> --tls-cert <p> --tls-key <p>
                  [--subnet 10.100.0.0/24] [--port 51820]
                  [--api-port 443] [--no-systemd]
                                   # DNS는 수동 안내(A 레코드 출력), TLS는
                                   # 기존 인증서 경로 지정 (§11 M0)
anago server run                   # 서버 상주 프로세스: 컨트롤 API + wg 인터페이스 유지
                                   # systemd 유닛의 ExecStart. `server init`이
                                   # 대신 설치·기동하므로 손으로 칠 일은
                                   # `--no-systemd`로 포그라운드 실행할 때뿐이다
anago code                         # 서버에서: 조인 코드 발급
anago join <domain> <code> [--name 맥북] [--api-port 443]
                                   # 서버가 --api-port로 초기화됐으면 같은 값을 준다
anago ls                           # 기기 목록 (기기에선 API, 서버에선 상태 파일)
anago rm <이름>                    # 기기 제거 (서버 반영)
```

M1이 더하는 표면:

```
anago server init --domain <d>
                  [--tls-cert <p> --tls-key <p>]      # 둘 다 주면 M0의 수동 경로,
                                                      # 둘 다 생략하면 ACME 자동 발급
                  [--acme-email <e>]                  # ACME 경로에서는 필수
                  [--acme-staging]                    # LE 스테이징 (join은 실패한다)
                  [--acme-challenge http-01|dns-01]   # 기본: 토큰 있으면 dns-01
                  [--cf-token <t> | --cf-token-file <p>]
anago server renew [--force] [--dns]
                   [--acme-staging | --acme-production]
                   [--acme-email <e>] [--acme-challenge http-01|dns-01]
                   [--cf-token <t> | --cf-token-file <p>]
                                   # 허브에서: 인증서 재발급·발급 설정 변경
                                   # --dns는 A 레코드만 다시 밀고 끝낸다
anago sync [--quiet] [--config <device.json 경로>]
                                   # 기기에서: 피어 목록을 당겨 wg 설정 갱신
anago sync --install-timer [--interval 5m] [--config <p>]
anago sync --uninstall-timer       # 주기 실행 설치·제거 (linux systemd / 맥 launchd)
anago join <domain> <code> --export qr|conf --name <이름> [--out <p>]
                                   # 폰(공식 wg 앱)용 설정 출력. 이 기기에는 적용하지 않는다
```

아직 미루는 표면(설계는 유지, 구현은 나중):

```
anago ping <이름>                  # M3: 사설 IP 조회 + ping 위임
anago server status                # M3: 피어·마지막 handshake·트래픽 대시보드
```

#### `server init` — 어느 TLS 경로로 갈지 고르는 규칙

**`--tls-cert`와 `--tls-key`는 둘 다 있거나 둘 다 없어야 한다.** 한쪽만
주는 것은 에러다(무엇을 의도했는지 추측하지 않는다). 그리고 이 한 쌍이
갈림길 전체를 결정한다:

- **둘 다 있으면** M0의 수동 경로다. `tls.source = "manual"`(§9.1),
  ACME는 아예 돌지 않으며 `--acme-*` 플래그가 함께 오면 에러다 — 조용히
  무시하면 사람은 자동 갱신이 켜진 줄 안다. **`--cf-token*`은 예외로
  같이 올 수 있다**: 토큰의 다른 일(A 레코드 자동화)은 인증서를 어디서
  얻었는지와 무관하고, 그것까지 막으면 "내 인증서를 쓰려면 DNS도 손으로
  해야 한다"는 관계없는 두 기능의 묶음이 된다.
- **둘 다 없으면** ACME 자동 발급이다. 이때 **`--acme-email`이 필수**다.
  Let's Encrypt는 연락처 없이도 계정을 만들어 주지만, 자동 갱신이
  조용히 망가졌을 때 사람에게 닿는 유일한 외부 경보가 CA의 만료 메일
  이다. anago의 약속이 "세우고 잊는다"인 만큼 그 경보를 기본값으로
  끄지 않는다 — 한 번 치는 플래그와 맞바꿀 것이 아니다.

챌린지 선택은 **Cloudflare 토큰이 있으면 `dns-01`, 없으면 `http-01`**
이 기본이다(§11 M1). `--acme-challenge`는 그 기본을 덮는 탈출구다 —
토큰은 있는데 zone 위임이 특이해서 HTTP-01로 받아야 하는 경우가 있고,
그때 "A 레코드 자동화를 포기해야 DNS-01을 피한다"는 식으로 관계없는 두
기능이 묶이면 안 된다. `--acme-challenge dns-01`을 토큰 없이 주면
에러다.

토큰은 세 경로로 받고 우선순위가 있다: **`--cf-token-file <p>` >
`--cf-token <t>` > 환경변수 `CLOUDFLARE_API_TOKEN`.** 두 플래그를 같이
주면 에러다. `--cf-token`은 편의이자 위험이라고 적어 둔다 — argv는
`ps`와 셸 히스토리에 남으므로 스크립트에는 `--cf-token-file`이 맞다.
셋 다 없으면 Cloudflare 자동화를 하지 않고 **M0의 수동 안내 경로가
그대로 나온다**(A 레코드를 이렇게 추가하라).

**이 규칙들을 어디서 검사하는지도 정해 둔다.** 규칙 자체는 두 순수
함수가 소유한다 — 토큰 두 플래그는 `cfapi::choose`, TLS 갈림길은
`acme::plan`. 라우팅(`cli`)은 **환경변수를 읽지 않는다.** 안 읽는 것이
라우팅의 모든 규칙을 유닛 테스트로 남기는 조건이기 때문이다. 그래서
라우팅은 그 두 함수를 argv만 가지고 한 번 돌려, argv로 판정되는 것
(한쪽만 준 인증서 쌍, 인증서 옆의 `--acme-*`, `--acme-email` 누락,
토큰 플래그 두 개)을 아무것도 생성되기 전에 거절한다. 판정 결과는
버린다 — 결정하는 것은 `init`이 환경변수까지 넣고 다시 돌리는 쪽이다.

**딱 하나, `--acme-challenge dns-01`에 토큰이 없다는 판정만 라우팅에서
하지 않는다.** 토큰은 `CLOUDFLARE_API_TOKEN`으로도 오는데 라우팅은
그걸 못 보므로, 여기서 거절하면 문서로 약속한 세 번째 경로가 막힌다.
이 판정은 `init`이 같은 `acme::plan`으로 내린다.

`--acme-staging`은 Let's Encrypt 스테이징으로 발급한다. 레이트 리밋을
태우지 않고 배선을 확인하는 용도이고, **그 인증서는 공개 신뢰가 아니라
`join`이 `UnknownIssuer`로 실패한다**(§11의 origin cert와 같은 이유).
init 출력이 그 사실을 크게 말한다. 스테이징 여부는 상태의
`tls.acme.directory`에 URL로 남으므로(§9.1) 갱신도 같은 CA로 간다 —
프로덕션으로 옮기는 것은 아래 `server renew --acme-production`이다.
다른 CA를 고르는 플래그는 M1에 두지 않는다. 스키마가 이미 URL을 담으니
필요해지면 플래그만 더하면 되고, M1이 풀려는 문제가 아니다.

#### `server renew` — 도입한다

**`anago server renew`를 M1에 넣는다.** 데몬이 알아서 갱신하는데도
사람이 부를 수 있는 명령이 필요한 이유는 넷이다.

1. `--no-systemd` 등 데몬이 상주하지 않는 배치에서는 갱신을 부를 것이
   아무것도 없다.
2. 갱신이 실패했을 때(전파 지연, 토큰 만료) 다음 주기를 기다리지 않고
   손으로 재시도할 길이 있어야 한다.
3. 스테이징에서 프로덕션으로 옮기는 일회성 전환.
4. M0로 세운 수동 허브를 ACME로 넘기는 전환.

`server init`을 다시 돌리는 것으로 대신하지 않는다. 두 번째 `init`은
기존 허브를 재키잉하지 않도록 **거부하는 것이 M0의 안전장치**이고(그
확인 항목이 `HUMAN-VERIFY.md`에 있다), init은 wg 키·systemd 유닛까지
건드리는 명령이라 "인증서만 다시 받고 싶다"와 크기가 맞지 않는다.

동작 규약:

- **아무 플래그 없이 부르면 판정부터 한다.** 갱신할 때가 아니면(§9.1의
  `renew_after`/`not_after`) 아무것도 하지 않고 "언제 갱신될 예정"인지만
  말한다. 그래서 이 명령은 멱등이고 cron으로 돌려도 안전하다.
- **`--force`**: 설정이 그대로여도 시점 판정을 무시하고 즉시 재발급한다.
  CA 레이트 리밋을 태울 수 있다는 경고를 함께 찍는다.
- **설정 플래그를 주면 시점 판정을 어떻게 하는가.** 기준은 한 줄이다 —
  **"이 설정으로 지금 발급하면 다른 인증서가 나오는가?"**
  - **나온다 → 즉시 재발급한다. `--force`는 필요 없다.** 해당하는 것은
    CA를 바꾸는 `--acme-staging`/`--acme-production`과 수동→ACME
    전환이다. 스테이징 인증서를 그대로 둔 채 상태에만 "프로덕션"이라고
    적는 것은 거짓이고, 사람이 그 명령을 친 이유(신뢰되는 인증서를
    지금 갖는 것)를 이루지 못한다. `--force`를 요구하는 것도 답이
    아니다 — 여기서 강제되는 것은 사람의 의도가 아니라 설정과 파일을
    다시 맞추는 일이라 물어볼 것이 없다.
  - **안 나온다 → 상태만 갱신하고 인증서는 그대로 둔다.** 해당하는 것은
    `--acme-email`, `--cf-token*`, 그리고 **`--acme-challenge`**다.
    챌린지는 인증서 내용에 영향이 없다 — 같은 CA가 같은 이름으로 주는
    같은 인증서이고, 바뀌는 것은 다음 갱신이 소유를 어떻게 증명하느냐
    뿐이다. 그러니 다음 갱신부터 적용된다.
  - 어느 쪽이든 **무엇을 했는지 한 줄로 말한다**: "재발급했습니다(만료
    …)" 또는 "설정만 바꿨습니다. 다음 갱신 예정 …". 말하지 않으면 두
    동작이 겉보기에 같다.
- **재발급을 동반하는 변경은 전부-아니면-전무다.** 발급에 실패하면
  상태도 바꾸지 않는다. 프로덕션이라고 기록해 놓고 스테이징 인증서를
  서비스하는 것이 최악의 상태이고, 이건 `server init`이 "실패하면 아무
  것도 남기지 않는다"로 지키는 성질과 같다.
  - **반대 방향도 막는다.** CA가 답한 뒤 상태 커밋이 실패하는 창이
    있다(잠금을 못 잡거나, 그 사이 설정이 바뀌었거나, 새 쌍이 로드되지
    않거나). 그러면 파일은 프로덕션인데 상태는 스테이징이고, **다음
    갱신이 기록된 CA에 없는 계정을 내민다.** 그래서 발급 직전에
    `account.key`·`fullchain.pem`·`privkey.pem`의 **이전 내용을 떠 두고,
    커밋 전에 실패하면 되돌린다.** init과 달리 지우는 것이 아니라
    **되돌리는** 것이다 — 이미 서 있는 허브에는 동작하는 계정과 인증서가
    있었다. 되돌리기에 실패하면 조용히 넘기지 않고 말한다(고칠 명령과
    함께).
  - 뜨는 경로는 **발급이 실제로 쓰는 경로**이고, 셋이 한곳에 있지
    않다. **인증서·키는 상태가 뭐라 하든 언제나 `/var/lib/anago/tls/`의
    그 쌍**이다 — `acme::renew`가 거기 저장하고 그 경로를 돌려주며
    `acme::record`가 상태를 거기에 맞춘다. 상태의 `cert_path`를 뜨면
    발급이 건드리지도 않은 파일 둘을 되돌리고 진짜 쌍은 새것인 채로
    남는다. **계정 키는 상태가 적은 경로**다 — 스키마가 자유롭게 두게
    하고 `acme::renew`는 읽은 그 경로에 되쓰므로, 기본 경로만 지키면
    진짜 계정 파일이 새 CA의 자격증명을 든 채로 남는다. 계정이 쌍 중
    하나를 가리키는 상태면 같은 경로를 두 번 뜨지 않는다. 계정 경로는
    `apply` **뒤**의 값을 쓴다(CA를 바꾸면 계정이 옮겨 가고, 수동 허브를
    인계받으면 없던 계정 경로가 생긴다).
  - **읽히지 않는 파일은 "없는 파일"이 아니다.** 있는데 못 읽으면 CA를
    부르기 **전에** 멈춘다. 없는 것으로 치면 나가는 길에 동작하는 계정을
    지우는 가드를 무장시키는 셈이고, 아직 시작도 안 한 실행을 접는 데는
    드는 것이 없다.
- **만료 전 점검은 상태 파일 밖으로 한 발짝도 안 나간다.** 플래그 없이
  부른 `server renew`가 갱신할 때가 아니면, 토큰도 안 읽고 zone 조회도
  안 하고 파일도 안 쓰고 커밋도 안 한다. "cron에 넣어도 안전하다"가
  그런 뜻이다 — Cloudflare가 잠깐 흔들렸다고 "아무것도 안 했습니다"라고
  보고하면서 실패하는 점검은 안전하지 않다.
- **토큰은 이 실행이 쓸 데가 있을 때만 읽는다.** DNS-01에서 나가는
  전환(`Forget`)은 버리는 토큰이 **읽히는지조차 묻지 않는다.** 토큰이
  만료됐거나 사라진 것이 애초에 HTTP-01로 돌아가는 이유이고, 버리려는
  것이 아직 동작해야 한다고 요구하면 이 명령이 열어 주려던 문을 닫는다.
- **쓸 데가 없는 토큰은 거부한다.** 결과 챌린지가 DNS-01이 아닌데
  `--cf-token*`을 주면 에러다. §9.1이 `token_path`를 DNS-01일 때만 두게
  하므로 넣을 자리가 없고, 받아 놓고 버리면서 "설정을 기록했습니다"라고
  찍는 것이 가장 나쁘다. 에러가 두 대안을 그대로 알려 준다 —
  `--acme-challenge dns-01`로 갱신에 쓰거나, `--dns`로 A 레코드에 쓰거나.
  이 검사는 **모든 재발급 분기보다 앞에** 둔다 — `--force`와 CA 변경은
  판정을 일찍 끝내므로, 뒤에 두면 그 둘만 검사를 지나쳐 토큰을 조용히
  버린다.
- **`--acme-staging`과 `--acme-production`**: 둘 다 주면 에러이고,
  **둘 다 안 주면 상태를 그대로 둔다** — 플래그의 부재를 "끄기"로 읽으면
  평범한 갱신 한 번에 CA가 조용히 바뀐다. `init`에 짝이 없는 이유는
  거기선 기본이 프로덕션이라 `--acme-staging`이 순수한 opt-in이기
  때문이다. 여기서만 기존 값을 덮어써야 해서 짝이 필요하다.
- 나머지 설정 플래그도 **준 것만 상태를 덮어쓰고, 안 준 것은 그대로**다.
- **DNS-01로 바꾸면 `cloudflare` 블록이 없던 허브도 생긴다.** 토큰 없이
  세운 허브를 `--acme-challenge dns-01 --cf-token-file …`로 옮기면
  challenge만 적고 끝낼 수 없다 — 첫 발급은 이 실행이 토큰을 직접
  넘겨 주므로 성공하고, **그 뒤 자동 갱신이 전부 "Cloudflare 설정이
  없다"로 실패한다**(§9.1의 `cloudflare_for`). 그래서 이 전환에서 zone을
  한 번 조회해 `zone_id`와 `token_path`를 함께 적는다. `record_id`는
  `null`이다 — anago가 그 이름에 아무것도 쓴 적이 없으므로 가리킬 id가
  없다.
- **DNS-01에서 나가면 토큰을 잊는다.** `token_path`를 `null`로 되돌리고,
  그 경로가 **anago가 쓴 파일**(`/var/lib/anago/cf-token`)이면 지운다.
  `--cf-token-file`로 받은 남의 파일은 참조만 끊고 건드리지 않는다.
  순서는 **커밋 먼저, 삭제 나중**이다 — 삭제가 실패해도 상태 파일은
  이미 옳고 남은 것은 경고 한 줄이지만, 반대로 하면 상태가 가리키는
  토큰이 없는 허브가 된다. 이 "잊기"는 **DNS-01에서 나가는 전환일
  때만** 돈다. HTTP-01 허브에서 아무것도 안 주고 부른 `server renew`는
  점검이고, 점검이 파일을 지우면 놀랍다.
- **토큰 우선순위는 §8 그대로 "명시 플래그 → 기록된 파일 → 환경변수"**다.
  기록된 경로는 두 플래그가 **모두 없을 때만** 후보가 된다. 안 그러면
  이미 DNS-01로 도는 허브에 `--cf-token <새 값>`을 주는 것이 "플래그
  두 개를 같이 줬다"로 거부되어, 토큰 교체에 상태 파일을 손으로 고치는
  단계가 끼어든다.
- **`--dns`: A 레코드만 다시 민다.** 인증서는 건드리지 않고, 시점 판정도
  하지 않는다. 이것이 필요한 이유는 **서버의 공인 IP가 바뀌는 일이 실제로
  있기** 때문이다 — VPS를 옮겼거나 주소가 재할당되면 `init`이 써 둔 A
  레코드는 이제 남의 기계를 가리키고, 그 상태에서 고칠 방법이 `init`을
  다시 도는 것(거부된다)밖에 없으면 사람은 대시보드로 간다. anago가
  토큰을 이미 갖고 있는데 그러는 것은 이상하다. upsert이므로 주소가
  그대로면 "이미 여기를 가리킨다"고만 말하고 아무것도 쓰지 않는다.
  - **다른 플래그와 같이 줄 수 없다.** `--dns`는 "DNS만"이라는 뜻이고,
    재발급이나 설정 변경과 섞으면 실패했을 때 무엇이 반영되고 무엇이
    안 됐는지가 흐려진다. 토큰 플래그만은 예외다 — 레코드를 밀려면
    토큰이 필요하고, 상태에 없을 수도 있다.
  - **토큰이 없으면 거부한다.** 상태의 `cloudflare.token_path`(§9.1)나
    플래그·환경변수 중 하나는 있어야 한다. 토큰 없이 할 수 있는 일이
    없으므로 M0처럼 안내를 찍는 것이 아니라 무엇을 주면 되는지 말하고
    멈춘다 — 이미 선 허브에서 "레코드를 손으로 고치세요"는 사람이 이미
    아는 사실이다.
  - **`wg`는 건드리지 않는다.** A 레코드는 컨트롤 API가 어디 있는지를
    말할 뿐이고 피어 설정과 무관하다. 이 명령 전체가 그렇다 — 아래
    참고.
- **`server renew`는 어떤 경로로도 `wg`를 건드리지 않는다.** 인증서도 A
  레코드도 피어 목록·주소·키와 무관하고, 인터페이스를 다시 올리면 그
  순간 모든 터널이 끊긴다. 상태 파일의 `peers`·`server`·`subnet`도 읽기만
  한다.
- **`tls.source`가 `"manual"`인 허브**에서 설정 플래그 없이 부르면
  거부한다 — 남의 인증서는 anago가 갱신하지 않는다(§9.1). `--acme-email`
  을 주면 그것을 **ACME로 전환하라는 뜻**으로 읽는다. 전환은 위 기준의
  "다른 인증서가 나온다" 쪽이므로(anago는 아직 인증서를 갖고 있지도
  않다) 전환과 발급을 함께, `--force` 없이 한다. 에러 메시지가 그 명령을
  그대로 알려 주므로 마법이 아니라 안내다. 되돌리기도 쉽다: 발급물은
  `/var/lib/anago/tls/`에 새로 쓰이고 원래 인증서 파일은 손대지 않으므로,
  상태의 `tls`를 예전 경로로 되돌리면 그만이다.

무엇이 언제 바뀌는지 예시로 고정한다:

```
anago server renew
    # 갱신 시점 전이면 아무 변화 없음. "다음 갱신 예정 …"만 출력

anago server renew --force
    # 즉시 재발급. issued_at·not_after·renew_after가 갱신된다

anago server renew --acme-production            # 스테이징으로 세운 허브에서
    # 즉시 재발급(프로덕션 CA). directory와 위 세 시각이 함께 바뀐다.
    # 발급에 실패하면 directory도 스테이징 그대로 남는다

anago server renew --acme-challenge dns-01 --cf-token-file /root/cf-token
    # 인증서는 그대로. challenge와 토큰 경로만 상태에 반영되고
    # 다음 갱신부터 DNS-01로 간다

anago server renew --acme-email jo@example.com  # 수동(M0) 허브에서
    # manual → acme 전환 + 즉시 발급. tls.source·cert_path·key_path가
    # /var/lib/anago/tls/ 아래로 바뀐다

anago server renew --dns                        # 서버 IP가 바뀐 뒤
    # A 레코드만 이 기계의 주소로 다시 민다. 인증서·wg 무영향
```

#### `anago sync`와 주기 실행

`anago sync`는 **기기에서** 도는 명령이다. `device.json`을 읽어
`GET /api/v1/peers`를 부르고, 달라진 게 있을 때만 wg 설정을 다시 쓰고
`wg syncconf`로 적용한다(§6.3). wg를 만지므로 root가 필요하다.

- **플래그 없이 부르면 사람용이다**: 변경이 없으면 없다고 한 줄, 있으면
  무엇을 바꿨는지 말한다. **`--quiet`는 타이머용**이고, 실제로 타이머
  유닛의 명령줄이 `anago sync --quiet --config <절대 경로>`다. tty를
  감지해 말수를 바꾸는 마법은 쓰지 않는다 — 유닛 파일을 열면 왜 조용한지
  가 그대로 보이는 편이 낫다.
- **`--config <경로>`: 읽을 `device.json`을 절대 경로로 지정한다.**
  §9의 XDG/`SUDO_UID` 규칙을 건너뛰는 탈출구이고, **타이머가 존재할 수
  있는 이유**다. 그 규칙은 "사람이 자기 셸에서 친다"를 전제하는데 타이머는
  그렇지 않다: 유닛은 root로, 사용자 세션 밖에서, `SUDO_UID` 없이 뜬다.
  systemd가 root 서비스에 `HOME=/root`를 주므로 §9 규칙을 그대로 적용하면
  `/root/.config/anago/device.json`을 보게 되고, 정작 가입한 사용자의
  파일은 영영 읽지 못한다. 환경에서 추측하지 않는다는 §9의 태도를
  지키려면 **경로를 명령줄에 박아 두는 것**이 맞다.
- **`--config`는 `sync`에만 둔다.** `ls`·`rm`은 사람이 자기 셸에서 치는
  명령이라 §9 규칙이 정확히 맞는 상황이고, 기계가 사용자 문맥 없이
  실행하는 명령은 `sync` 하나뿐이다. 필요가 생기면 그때 넓힌다.
- **`--install-timer` / `--uninstall-timer`**는 상호 배타다. **양쪽 다
  시스템 수준(root)**이다 — sync가 wg 설정을 적용하려면 root여야 하므로
  맥에서도 사용자 LaunchAgent가 아니라 시스템 데몬이다. 이름과 위치를
  못박는다:
  - 리눅스: `/etc/systemd/system/anago-sync.service` +
    `anago-sync.timer`.
  - 맥: `/Library/LaunchDaemons/com.github.elpalaiso.anago.sync.plist`,
    라벨은 파일 이름과 같은 `com.github.elpalaiso.anago.sync`. 역-DNS
    라벨은 관례상 자기가 소유한 도메인을 쓰는데 anago는 도메인을 갖고
    있지 않으므로(§13의 이름 항목) 리포지토리 네임스페이스를 쓴다 —
    갖지 않은 이름을 선점하지 않는다.
- **설치는 경로를 그 자리에서 확정해 유닛에 굽는다.** `--config`를 직접
  주면 그 값을, 아니면 §9 규칙으로 해석한 절대 경로를 쓴다 — 설치는 보통
  `sudo anago sync --install-timer`라 `SUDO_UID`가 있고, 그래서 **설치
  시점에는** 가입한 사용자의 파일을 정확히 찾을 수 있다. 설치된 유닛은
  이렇게 읽힌다:

  ```
  ExecStart=/usr/local/bin/anago sync --quiet \
            --config /home/jo/.config/anago/device.json
  ```

  맥의 LaunchDaemon도 같은 인자를 `ProgramArguments`에 그대로 담는다.
  **유닛 파일 하나만 열면 어느 기기의 무엇을 동기화하는지 보인다** —
  `--quiet`를 명령줄에 둔 것과 같은 이유다.
- **유닛 두 짝의 내용도 여기서 못박는다** — 리눅스 기준, 나머지는 텍스트를
  만드는 순수 함수(`systemd.rs`)와 그 유닛 테스트가 곧 명세다.
  - `anago-sync.service`는 `Type=oneshot`이고 **`[Install]` 절이 없다.**
    타이머가 부르는 유닛이라 enable하면 부팅 때 한 번 돌고 그걸로 끝이다.
    `Restart=`도 두지 않는다 — 재시도 정책이 곧 타이머이고, 401로 끝난
    실행을 `on-failure`로 되살리면 이미 지운 기기 때문에 허브를 두들긴다.
  - **`TimeoutStartSec=`은 생략할 수 없다.** systemd는 `Type=oneshot`에
    한해 시작 타임아웃을 **아예 끄기** 때문이다. 멈춰 선 실행은 sync
    잠금을 쥔 채 남고, 그러면 §6.3대로 이후 실행이 전부 조용히 0으로
    끝나서 **타이머가 멀쩡해 보이는 채로 죽는다.** 클라이언트 자체 한도
    (연결 10초·읽기 30초) 위에 얹는 상한이라 2분으로 둔다.
  - **네트워크 의존은 두지 않는다.** 허브에 못 닿는 것은 §6.3에서 조용한
    0이므로 `network-online.target`을 기다려 얻을 것이 없다 — 다음 tick이
    가져올 것을 부팅 때 한 번 앞당기는 값이다. 못 닿으면 설 수 없는 허브
    유닛(§6.1)과 갈리는 지점이다.
  - 샌드박스는 `ProtectSystem=strict`·`ProtectHome=tmpfs` 위의 세 줄이다:
    `BindPaths=<device.json의 디렉터리>`(읽기·쓰기 — `device.json`을 다시
    쓰고 sync 잠금을 그 옆에 잡는다), `ReadWritePaths=<wg 디렉터리>`(설정과
    그 옆에 쓰는 strip 사본), `BindReadOnlyPaths=<실행 파일>`. 홈 아래 있을
    수 있는 것은 bind로, `/etc` 아래로 정해진 것은 예외로 — bind는 홈이
    아닌 디렉터리에도 그대로 통하므로 갈래 없이 한 규칙이 된다.
    **권한(capability)은 손대지 않는다**: 실행이 커널 인터페이스를
    재설정하므로 `CAP_NET_ADMIN`·`CAP_CHOWN`·`CAP_DAC_OVERRIDE` 중 무엇이
    남아야 하는지 짐작하는 것은 아무도 안 보는 기계에서 타이머가 조용히
    죽는 길이다. 정직하게 좁힐 수 있는 것은 파일 시스템뿐이고, 좁힌 것도
    그것뿐이다.
  - **`device.json`이 `/` 바로 아래 있으면 설치하지 않는다.** 열어 줄
    디렉터리가 `/`가 되는데, 그러면 `ProtectSystem=strict`가 파일에 적힌
    채로 전체 파일 시스템을 내준다 — 없는 것보다 나쁘다. **있는 것처럼
    읽히기** 때문이다.
  - **맥의 plist도 여기서 못박는다.** `ProgramArguments`는 인자 하나가
    원소 하나라 셸도 단어 분리도 끼지 않는다 — 공백이 든 경로에 따옴표가
    필요 없고, 리눅스 유닛이 이스케이프로 피해 다니는 문제 자체가 생기지
    않는다. 남는 것은 XML의 것이다: `&`·`<`는 엔티티로 쓰고, **제어 문자
    대부분은 XML 1.0에 표현 자체가 없으므로**(엔티티로도 못 쓴다) 거부한다.
    줄바꿈은 여기서 **받는다** — 유닛과 갈리는 지점이고, 이유는 plist가 줄
    단위로 읽히지 않기 때문이다. UTF-8이 아닌 경로는 거부한다(첫 줄이 스스로
    UTF-8이라고 선언하는 파일이다).
  - **탭·줄바꿈·복귀는 문자 참조(`&#9;`·`&#10;`·`&#13;`)로 쓴다.** XML
    처리기는 문서를 읽기 **전에** 줄 끝을 정규화한다 — 날 `#xD`와 `#xD #xA`가
    똑같이 `#xA` 하나가 된다. 그래서 복귀 문자가 든 경로를 글자 그대로 적으면
    launchd에는 **다른 경로**가 도착하고, `a\r\nb`와 `a\nb`가 **같은** 경로로
    도착한다. 문자 참조는 그 단계 다음에 풀리므로 살아남는다. 셋을 같이
    처리하는 이유는 규칙이 하나면 되기 때문이다.
  - **`StandardOutPath`·`StandardErrorPath`가 없으면 아무 말도 남지 않는다.**
    launchd는 데몬의 stdout·stderr를 `/dev/null`로 보내므로, 그러면 §6.3의
    종료 코드 규약은 살아 있는데 "이 기기가 제거됐다"는 **그 한 줄이 아무
    데도 안 쓰인다.** systemd는 저널을 공짜로 주지만 여기서는 요청해야 한다.
    `/var/log/anago-sync.log` 한 파일에 둘 다 보낸다 — 두 스트림의 순서가
    남고 볼 곳이 하나다. 회전시키는 것은 없지만 `--quiet`에서는 진짜 문제가
    있을 때만 쓰이므로, 그 사실은 설치 출력이 말한다.
  - `StartInterval`은 **초 정수**다. 단위를 적을 자리가 없으니 리눅스에서
    걱정한 "맨 숫자가 초로 읽힌다"가 여기서는 오히려 유일한 읽기다.
    `RunAtLoad`는 `OnBootSec=`의 짝이다 — 없으면 설치 후 첫 주기가 다
    지나야 처음 돈다. `KeepAlive`는 두지 않는다: 끝나는 것이 정상인
    작업이라 되살리면 안 되고, 일정은 간격이 정한다(`Restart=`를 안 두는
    것과 같다). 실행 중에 간격이 지나면 launchd는 두 번째 복사본을 띄우지
    않고, 자는 동안 지난 주기는 깨어날 때 한 번만 돈다 — 둘 다 §6.3에서
    따라잡을 것이 없다.
  - 적재는 **`launchctl bootstrap system <plist>`**, 해제는
    **`launchctl bootout system/<label>`**이다. `load`/`unload`는 아직
    동작하지만 실패할 때 아무것도 알려주지 않아서, 사람이 한 번 치는 명령에
    쓰기에는 나쁜 거래다. **두 명령의 모양이 다르다는 점이 함정이다** —
    bootstrap은 도메인과 파일을, bootout은 서비스 타깃을 받는다. bootout은
    launchd에서 빼기만 하므로 **plist 파일은 따로 지워야 한다**(안 지우면
    다음 부팅에 돌아온다).
  - **bind 목록에 들어갈 경로에 콜론이 있으면 거부한다.** `BindPaths=`·
    `BindReadOnlyPaths=`의 항목은 `source:destination:options`라서
    `/home/jo/a:b`는 `/home/jo/a`를 `b`에 붙이라는 뜻이 되고, destination이
    절대 경로가 아니므로 systemd는 **그 줄을 통째로 버린다.** 버리는 게
    문제다 — 유닛은 설치되고 기동되며 `ProtectHome=tmpfs`가 정작 그 bind로
    되살리려던 디렉터리를 가린 채로 남는다. 타이머는 5분마다 실패하는데
    이유를 알아보려고 연 파일은 멀쩡해 보인다. 백슬래시나 따옴표가 콜론을
    그 파서 너머로 넘겨 줄 수도 있지만, "줄 수도 있다"는 것은 실기계에서
    확인할 수 없는 채로 root 유닛에 굽을 성질이 아니다. **콜론이 bind에
    닿지 않는 자리(`ExecStart=` 인자, `ReadWritePaths=`)에서는 거부하지
    않는다** — 그 줄에서는 참이 아닌 이유로 합법적인 경로를 막는 것이 된다.
  - **모든 `ExecStart=`는 `:` 접두사로 변수 확장을 끈다.** 경로에는 달러
    기호가 합법적으로 들어갈 수 있는데(`/home/jo/${USER}/device.json`),
    명령줄은 `${...}`를 치환한다 — 시스템 유닛이면 root 계정 값으로, 변수가
    없으면 **빈 문자열로**. 게다가 `BindPaths=`·`ReadWritePaths=` 같은 경로
    설정은 변수를 확장하지 않으므로, 접두사가 없으면 **같은 `--config`에서
    샌드박스가 연 디렉터리와 실행 인자가 읽는 경로가 갈린다.** `$$`로
    이스케이프하는 길도 있지만 그러면 두 줄이 같은 경로를 다르게 적게 되고,
    경로 설정에서는 `$$`가 달러 두 개다 — 접두사 쪽이 한 군데서 끝나고 유닛을
    읽는 사람에게도 두 줄이 같은 글자로 보인다. `%`는 반대다: 모든 설정에서
    지정자로 확장되므로 렌더링 단계에서 `%%`로 이중화한다. systemd 231(2016)
    이상이 필요하고, 그 아래에서는 경로가 절대경로가 아니라며 **설치 시점에
    시끄럽게** 실패한다.
  - **유닛이 이름 붙일 수 없는 경로는 유닛을 만들기 전에 거부한다.** 유닉스
    파일명에는 슬래시와 NUL 말고 뭐든 들어갈 수 있는데, `--tls-cert`·
    `--config`는 그것을 명령줄에서 그대로 받는다. systemd는 유닛을 **한 줄씩**
    읽으므로 경로 안의 줄바꿈은 따옴표로 감싸도 살아남지 못한다 — 뒷부분이
    별도 지시자가 되어 root 유닛을 깨뜨리거나 아무도 지정하지 않은 디렉터리를
    `BindPaths=`로 열어 준다. 그래서 **제어 문자가 든 경로와 UTF-8이 아닌
    경로는 렌더링하지 않고 거부한다**(후자는 `to_string_lossy`가 *다른* 경로를
    적어 넣기 때문이다 — 없는 바이너리를 가리키는 `ExecStart`와 없는 디렉터리를
    지키는 샌드박스가 되고, 그렇다고 말해 주는 곳이 없다). 허브 유닛(§6.1)도
    같은 관문을 지나며, 거부는 파일을 쓰기 **전에** 일어나므로 반쯤 설치된
    유닛은 남지 않는다. 거절 문구 자체도 한 줄이다 — 줄바꿈이 든 경로를 그대로
    출력하면 같은 실수를 한 겹 위에서 되풀이하는 것이라, 경로는 이스케이프해
    보여 준다.
  - `anago-sync.timer`는 `OnBootSec=`과 `OnUnitActiveSec=`을 같은 값으로
    둔다. `OnUnitActiveSec=` 하나로는 기준이 될 "마지막 실행"이 없어 영영
    뜨지 않고, `--install-timer`를 치는 기계는 대개 부팅한 지 그보다
    오래됐으므로 이 씨앗은 이미 지나 **첫 sync가 즉시 돈다.**
    `Persistent=`는 두지 않는다 — 달력 타이머의 것이라 여기서는 아무 일도
    안 하고, 자다 깬 노트북이 밀린 폴링을 따라잡을 이유도 없다(§6.3).
  - 주기는 **단위를 붙여 적는다**(`90s`·`5min`·`1h`). systemd도 맨 숫자를
    초로 읽으므로, 단위를 안 적으면 `--interval`이 거부하는 바로 그 오해가
    유닛 파일에서 되살아난다.
- **해석한 경로에 파일이 없으면 설치하지 않는다.** 아무것도 가리키지
  않는 타이머를 깔아 두는 것은 안 까는 것보다 나쁘다 — 5분마다 조용히
  실패하는데 사람은 동기화가 되는 줄 안다. join을 먼저 하라고 안내하고
  멈춘다.
- 실행 시점에 그 파일이 사라졌으면(사람이 지웠거나 다시 가입했다) sync는
  **이유를 말하고 조용한 실패로 끝낸다** — 타이머를 스팸하지 않는 종료
  코드 규약은 위 `--quiet`와 같은 결이다. 고치는 길은 `--uninstall-timer`
  후 재설치다.
- 한 기기에 여러 사용자가 각자 join한 경우는 M1의 대상이 아니다. 타이머는
  설치할 때 확정한 `device.json` **하나**를 본다.
- 둘 중 어느 쪽도 아닌 환경(비-systemd 리눅스, 컨테이너)에서는 **설치를
  흉내 내지 않고** cron 한 줄을 안내하고 멈춘다 — 그 한 줄에도 같은
  `--config` 절대 경로가 들어간다. `--no-systemd`가 `server init`에서
  하는 것과 같은 태도다.
- **비-systemd·비-맥에서 안내하는 cron 한 줄에도 규칙이 있다.** cron은
  스톱워치가 아니라 시계로 반복하므로 `*/7 * * * *`은 "7분마다"가 아니라
  0·7·…·56분이고 정시에 4분이 벌어진다. **한 시간을 나누는 분**이나 **하루를
  나누는 시간**만 표현 가능하고, 그 밖의 주기(`90s`, `7m`, `5h`)는 **거부한다**
  — 다른 주기를 조용히 대신 지키는 것은 답이 아니다. 같은 주기가 systemd나
  launchd에서는 그대로 되므로, 거부는 이 플랫폼에 한한 것이라고 말한다.
  명령 부분은 두 번 읽힌다: cron이 먼저 읽고(**이스케이프하지 않은 `%`는
  명령을 끝내고** 뒤를 표준입력으로 돌린다 — 경로에 `%`가 있으면 줄이 조용히
  짧아진 채로 여전히 돈다) 그다음 `/bin/sh`가 읽는다(공백이 든 경로는 두
  인자가 된다). 그래서 `%`는 `\%`로, 셸 단어는 필요할 때만 작은따옴표로
  감싸고(`'\''`로 따옴표 자체를 넘긴다), **제어 문자가 든 경로는 거부한다**
  — crontab도 줄 단위로 읽히므로 유닛과 같은 이유다.
  **백슬래시가 든 경로도 거부한다.** cron의 이스케이프 패스는 백슬래시
  **다음 문자**를 소비하므로, 경로에 원래 있던 백슬래시가 무엇이 소비되는지를
  어긋나게 만든다 — `…/a\%b`를 `…/a\\%b`로 적으면 첫 백슬래시가 둘째를 먹고
  `%`가 맨몸으로 남아 명령이 하필 그 자리에서 잘린다. 이걸 맞히려면 여기서
  돌려 볼 수 없는 파서에 root로 도는 줄을 걸어야 하므로, 걸지 않는다:
  백슬래시가 없으면 그 줄의 `\%`는 전부 이 코드가 넣은 것이다. systemd와
  launchd는 백슬래시가 든 경로를 그대로 받으므로 **거부는 crontab에
  한한다**.
- **이미 설치된 스케줄 위에 덮어쓰지 않는다.** 덮어쓰면 쓰기 **다음**
  단계가 실패했을 때 옛 스케줄도 새 스케줄도 남지 않고, 옛 내용을 도로
  써 넣는 것으로는 복구되지 않는다 — 그때는 이미 systemd가 reload했거나
  launchd가 새 파일을 집어 갔다. 그래서 답은 이미 있는 허브에 대한
  `server init`의 답과 같다: 멈추고, 길을 비우는 명령을 알려 준다.
  **주기를 바꾸는 것은 `--uninstall-timer` 후 재설치**이고, 두 절반이 각각
  무엇을 했는지 말한다.
- **설치가 실패하면 이번 실행이 한 일을 되돌린다.** 위 규칙 덕에 "이번
  실행이 한 일을 되돌린다"와 "기계를 원래대로 둔다"가 같은 목록이 되고,
  남의 파일 사본이 필요 없다. 한 일의 역순으로 셋이다:
  0. (그 전에) **유닛·plist는 umask가 아니라 명시한 모드로 쓴다.** 0644,
     원자적 교체. 그리고 **create 다음에 실패하는 단계는 create를 되돌린다**
     — 임시 형제 파일을 만들어 rename하는 구조라, 그 사이에서 실패하면
     "아무 일도 없었다"는 오류를 내면서 `<이름>.tmp`가 남는다. 거짓이고,
     rewind는 최종 경로만 알므로 영영 안 치워진다. root가 무엇을 실행할지 정하는 파일이라 group/world 쓰기
     가능이면 아무 사용자나 다음 reload 전에 바꿔 쓸 수 있고, launchd는
     그런 데몬을 아예 거부한다. 읽기까지 막지 않는 이유는 §8이 안내하는
     `systemctl cat anago-sync.service`가 막히기 때문이고, 그 파일에는 경로
     말고 아무것도 없다.
  1. **활성화.** 실패한 `enable --now`는 아무 일도 안 한 게 아니다 —
     만들던 symlink 일부가 남을 수 있고, 그 밑의 유닛 파일을 지우면 끊긴
     링크가 된다. 그래서 `disable --now`가 먼저다. launchd도 같다:
     bootstrap을 시도했으면 bootout이 먼저고, 안 그러면 실패로 보고된
     plist가 다음 부팅에 로드된다.
  2. **파일.** 조건 없이 전부. 중간에 실패한 쓰기도 파일을 남기고, 위
     규칙이 "전에는 아무것도 없었다"를 보장하므로 그 경로에 있는 것은
     전부 이번 실행의 것이다.
  3. **매니저의 인식.** 이미 보라고 시킨 경우에만 — 아니면 애초에 모르는
     일이라 고칠 것이 없다.
  되돌리기 자체가 실패하면 **무엇이 남았는지 말한다.** 롤백이 반쯤 된
  기계야말로 사람이 들어야 하는 상태다.
- **제거는 없던 것에는 관대하고, 확인 못 한 것에는 관대하지 않다.** 반쯤
  설치됐거나 이미 없는 것은 오류 없이 나가야 한다(수리 절차가 제거 후
  재설치이므로). 용서하지 않는 것은 **있는데 안 지워지는 파일**과 **안
  멈추는 스케줄**이다 — **"파일이 사라졌다"는 "안 돌고 있다"와 다른
  문장이다.** plist를 지워도 그것이 띄운 데몬은 계속 돈다(bootout이 존재하는
  이유가 그것이다).
  - 그래서 stop이 실패하면 **끝났다고 치지 않고 물어본다**: `systemctl
    is-active anago-sync.timer`, `launchctl print system/<label>`.
  - **그 확인의 non-zero도 "없다"가 아니다.** 두 명령은 대상이 없을 때만이
    아니라 매니저에 못 닿을 때, 물을 권한이 없을 때, 밑의 IPC가 깨졌을 때도
    실패한다. 그래서 인정하는 답은 셋뿐이다: 종료 0(있다), systemd가
    stdout에 찍는 **상태 낱말**(`inactive`·`failed`·`unknown` — 못 물어봤으면
    stdout이 비어 있다), launchctl이 **못 찾았다고 이름 대는 문구**. 그
    밖은 전부 "모름"이다. 문구로 부재를 알아보는 것이 여기서는 안전한
    방향이다 — 모르는 문구는 "모름"이 되므로, 이 목록은 사실보다 **덜**
    용서할 수는 있어도 더 용서할 수는 없다.
  - 아직 있거나 **확인하지 못했으면 실패로 끝낸다**(파일은 그대로 지운다 —
    어느 상태든 파일이 없는 쪽이 요청받은 상태에 가깝다). 다만 **두 문장은
    다르다**: "아직 로드돼 있다"는 기계에 대한 사실이고, "확인하지 못했다"는
    그 사실이 없다는 뜻이다. 확인 못 한 것을 확인한 것처럼 말하지 않는다.
  - 파일이 원래 없었더라도 stop은 시도하고 그 답을 읽는다. **파일은 없는데
    로드는 돼 있는** 경우가 실제로 있다(사람이 유닛만 지운 경우), 그리고 그때
    "설치된 적 없다"고 보고하면 거짓이다. 그리고 제거는
  **실제로 지운 것만 말한다** — cron 한 줄은 anago가 쓴 적이 없으므로
  치웠다고 말하지 않는다. 보이지도 않는다.
- **`--interval <5m>`**은 `--install-timer`와 함께일 때만 의미가 있고,
  단독으로 주면 에러다. 기본은 5분(§6.3). **단위를 요구한다** — 맨 숫자는
  관례상 초로 읽힐 수밖에 없는데, 기본이 5분인 명령에서 `--interval 5`가
  5초를 뜻하는 것은 허브 API를 분당 열두 번 두들기기 시작할 때까지
  아무도 눈치채지 못하는 종류의 실수다. **1분 미만과 하루 초과는
  거부한다**: 아래는 대부분의 변화가 기기에 아무 일도 안 시키므로(§6.3)
  폴링밖에 안 되고, 위는 피어 목록이 하루치 낡는다는 뜻이라 타이머라고
  부를 수 없다.
  `--interval`은 **`--install-timer`일 때만** 받는다 — 제거와 함께 주면
  곧 없어질 타이머의 주기이므로 그것도 무시될 값이다.
- **무시될 플래그는 받지 않고 거부한다.** `--quiet`는 실행에 붙는 것이지
  타이머 관리에 붙는 것이 아니고(조용한 설치는 "이렇게 확인하세요"를
  삼켜 버리는데 그게 설치가 출력하는 이유다), `--config`는 실행과
  `--install-timer`의 것이다 — 제거는 이름이 고정된 유닛을 지우는 일이라
  기기 파일을 읽지 않는다. 받아 놓고 버리면 성공한 플래그와 구별되지
  않는다.
- **`--config`는 절대 경로여야 한다.** 상대 경로는 작업 디렉터리 기준으로
  풀리는데, 이 플래그가 존재하는 이유 자체가 타이머에는 사람이 알아볼
  작업 디렉터리가 없다는 것이다(root로, 세션 밖에서, `/`에서 뜬다).
  유닛에 상대 경로를 굽는 것이 이 플래그가 막으려던 실패다.
- **`join`은 타이머를 안내하되 설치하지 않는다.** §6.3대로 주기 sync는
  편의이지 정합성 요건이 아니다 — 허브가 모든 기기를 라우팅하므로 한 번도
  sync하지 않는 기기도 나머지 전부에 닿는다. 그래서 둘이 따라온다.
  - 가입의 부수 효과로 **root 주기 작업을 남기는 것**은 요청받은 것보다 큰
    걸음이고, 무엇보다 터널을 세우는 것이 전부인 명령에 **터널과 무관한
    실패 경로**를 붙이는 일이다. `server init`이 유닛을 설치하는 것은 정반대
    이유다: 안 도는 허브는 허브가 아니지만, sync 안 하는 기기는 여전히
    네트워크 위에 있다.
  - 안내는 **그것이 인쇄되는 기계에서 참이어야 한다.** 이미 있는 타이머를
    깔라고 하거나(재설치는 거부된다) 깔 수단이 없는 기계에 설치를 권하는
    것은, 사람이 유일하게 주의를 기울이는 그 순간을 낭비한다.
  - 그리고 **파일이 닿는 데까지만 주장한다.** 유닛을 찾은 것은 도는
    스케줄을 찾은 것이 아니다 — 무장 해제돼 있을 수도, 맥의 시스템 설정에서
    꺼져 있을 수도, **다른 사용자의 `--config`를 물고 있을** 수도 있다(그러면
    가입한 적 없는 파일을 동기화한다). 그래서 "있다"에서 멈추고 나머지를
    답하는 명령을 넘긴다: `systemctl is-active anago-sync.timer` +
    `systemctl cat anago-sync.service`, 맥은 `sudo launchctl print
    system/<label>` 하나가 상태와 `ProgramArguments`를 함께 보여 준다. 답이
    틀렸으면 고치는 길은 제거 후 재설치이므로 `--install-timer`는 **혼자
    나오지 않는다**(혼자면 거부된다).
  - **반쪽 설치는 따로 말한다.** `anago-sync.timer`만 있고 서비스가 없으면
    아무것도 안 돌지만 파일은 남아 있으므로, "뭔가 있다"가 "당신은 커버돼
    있다"로 읽힌다. 그래서 상태는 셋이다: 없음 / 일부 / 파일 전부.
  - 안내는 세 갈래다: 스케줄러가 있고 아무것도 없으면 `sudo anago sync
    --install-timer`, 일부나 전부 있으면 위의 확인·수리, 스케줄러가 둘 다
    없으면 그 사실과 cron 안내가 나온다는 것.
  - 터널이 안 서면 안내하지 않는다. 그때 사람에게 필요한 것은 이것이 아니다.
- 타이머가 설치됐는지 보는 별도 표면은 두지 않는다. 설치 명령이 확인
  방법을 출력하면 충분하고, §6.3대로 timer는 편의이지 정합성 요건이
  아니다. 다만 그 문구는 **도메인과 라벨까지 정확해야** 쓸모가 있다:
  - 리눅스: `systemctl list-timers 'anago-sync*'`, 명령줄까지 보려면
    `systemctl cat anago-sync.service`.
  - 맥: **`sudo launchctl print system/com.github.elpalaiso.anago.sync`**.
    `sudo`와 `system/`이 둘 다 필요하다 — 일반 사용자 셸의
    `launchctl list`는 사용자 bootstrap 문맥(`gui/<uid>`)을 보므로 시스템
    데몬인 이 서비스를 찾지 못한다. `print`의 출력에 `ProgramArguments`가
    함께 나오므로 `--config` 경로도 같은 자리에서 확인된다.

#### `join --export qr|conf` — 폰 경로

`--export`가 붙은 `join`은 **이 기기를 등록하는 명령이 아니라, 폰을
대신 등록해 주는 명령**이다. 그래서 로컬에는 아무것도 남기지 않는다:
wg 설정도 쓰지 않고 `device.json`도 쓰지 않으며, 따라서 §6.2의 중복
가입 방지도 이 경로에는 걸리지 않는다(이름 중복은 서버가 막는다, §8.1).

- **`--name`이 필수다.** 이름을 생략하면 이 노트북의 호스트명이 들어가는
  데, 등록되는 것은 폰이므로 그 기본값은 언제나 틀렸다.
- **`--export conf`**는 완결형 wg 설정을 표준출력에 낸다. `--out <p>`를
  주면 대신 그 파일에 0600으로 쓰고 표준출력에는 아무것도 내지 않는다
  (이미 있는 파일은 덮어쓰지 않고 에러). 셸 리디렉션(`>`)으로 만든
  파일의 모드는 anago가 정하지 못하므로 §7.3이 그 경고를 규정한다.
- **`--export qr`**는 같은 설정을 QR로 그린다. **`--out`과 함께 쓰면
  에러다** — 이미지 파일을 만들지 않는다(§10.2대로 이미지 크레이트를
  들이지 않는다). 좁은 요청이 아니라 불가능한 요청이므로 무시가 아니라
  거절이다: 받고 버리면 통한 플래그와 구별되지 않아서, 영영 만들어지지
  않을 파일을 찾게 만든다.
- **`--out`은 `--export` 없이는 아무 뜻도 아니다.** 로컬 join은 §9가 정한
  자리에 쓰므로 `--out`이 방향을 바꿀 출력 자체가 없다. `--name`과
  `--api-port`는 두 모드가 함께 쓰지만 `--out`은 `conf`의 것이다.
- **기기 토큰은 버린다.** join 응답에 토큰이 오지만 공식 wg 앱은 anago의
  컨트롤 API를 부르지 않으므로 쓸 데가 없다. 출력하지도 저장하지도
  않는다. 결과로 **그 폰은 스스로 `ls`/`rm`/`sync`를 하지 못하고**,
  지우는 것은 허브에서 `anago rm <이름>`이다. 허브-스포크라 sync가 없어도
  통신에는 지장이 없다(§6.3).
- 이 경로는 §6.2의 "개인키는 기기를 떠나지 않는다"에 대한 **의도된
  예외**다 — 폰의 개인키가 이 기기에서 만들어져 화면이나 파일로 나간다.
  `--out`의 0600·덮어쓰기 금지, 경고를 stderr로 내는 규약, 스크롤백과
  conf 파일 정리 안내는 §7.3이 정한다.

M0에서 `sync`가 없어도 통신은 된다 — §6.3의 성질 그대로다. 허브가
피어를 다 알고 서버가 자기 wg 설정을 갱신하므로, 기기 쪽 설정이
`AllowedIPs = <subnet>` 한 줄이면 새 기기와도 바로 통신된다. 기기
설정을 다시 만져야 하는 경우는 M2(직결 엔드포인트)부터다.

컨트롤 API(v1, JSON over HTTPS — 스키마는 anago-core의 타입이 원본):

| 메서드/경로 | 마일스톤 | 인증 | 역할 |
|---|---|---|---|
| POST /api/v1/join | M0 | 조인 코드 | 공개키 등록 → IP 할당·서버 정보 응답 |
| GET  /api/v1/peers | M0 | 기기 토큰 | 피어 목록(공개키·IP·이름). M1에서 허브 자신의 값 넷(`subnet`·`server_public_key`·`server_endpoint`·`server_address`)이 최상위에 더해진다 — 정확한 형태와 부재 규칙은 §6.3 |
| DELETE /api/v1/peers/{name} | M0 | 기기 토큰 | 기기 제거 |
| POST /api/v1/endpoint | M2 | 기기 토큰 | 자기 관측 엔드포인트 보고 |

`GET /api/v1/peers` 응답에 **기기가 관측한** 엔드포인트 필드는 M2까지
없다(§9.1과 같은 이유 — 그건 기기가 보고하는 새 쓰기 경로다). 반면
**허브 자신의** 값 넷은 M1에서 응답 최상위에 더한다: `subnet`,
`server_public_key`, `server_endpoint`, `server_address`. `anago sync`가
로컬 설정을 허브와 대조하려면 비교 대상이 있어야 하기 때문이고, 넷 다
`JoinResponse`가 이미 같은 이름으로 보내는 값이라 새로 정할 의미가 없다.
넷은 함께 있거나 함께 없으며, 없는 응답(M0 허브)을 받은 M1 클라이언트가
어떻게 행동하는지까지 §6.3이 정한다.

### 8.1 기기 이름 규칙

이름은 `rm`의 키이자 URL 경로 조각(`DELETE /api/v1/peers/{name}`)이고,
M3에서는 호스트명이 된다. 그래서 규칙을 여기서 못박는다.

- **정규형**: 앞뒤 공백을 떼고 소문자화한 형태. 서버는 정규형을 저장하고
  join 응답의 `name`으로 돌려준다 — 클라이언트는 보낸 이름이 아니라
  받은 이름을 저장한다.
- **길이**: 1–32자(문자 수 기준).
- **허용 문자**: 유니코드 문자·숫자와 `-`, `_`. 첫 자와 끝 자는 문자
  또는 숫자여야 한다. 한글 이름(`맥북`)은 1급 시민이다 — 문서의 예시가
  그렇게 쓰고 있고, 개인용 도구에서 이름은 사람이 읽는 것이다.
- **금지 문자와 이유**: `.`은 M3의 라벨 경계(`맥북.net.example.com`)와
  충돌하고, `/` `%` `?` `#` `:`는 URL 경로를 깨며, 공백·제어문자는 wg
  설정과 셸 인용에서 사고를 낸다.
- **예약어**: `server`. 허브 자신을 가리키는 이름이라 M3의 이름 해석에서
  충돌한다.
- **중복**: 정규형이 같으면 같은 이름이다. `MacBook`과 `macbook`은
  공존할 수 없다.

**알려진 한계(M0)**: 유니코드 정규화(NFC/NFD)는 하지 않는다. 표준
라이브러리에 정규화가 없고 코어는 순수 std이기 때문이다(§4 원칙 4).
따라서 조합형으로 입력한 `맥북`과 완성형 `맥북`은 눈에는 같아 보여도
서로 다른 이름으로 등록될 수 있다. 실사용에서 문제가 되면 그때
바이너리 크레이트에 정규화 의존성을 두고 이 문단을 고친다.

**M3 메모**: 비-ASCII 이름의 DNS 라벨화(punycode)는 M3에서 다룬다. M0는
저장·표시·조회만 한다.

## 9. 서버 상태와 설정

- 상태: `/var/lib/anago/state.json` — 단일 파일, 원자적 쓰기
  (tmp+rename), 0600, 동시 쓰기는 flock으로 직렬화. DB 없음.
- 인증서: 상태는 **경로만 기록한다 — 사람이 준 인증서 파일을 복사하지
  않는다.** M1의 ACME 발급물만 anago가 소유하며 `/var/lib/anago/tls/`
  (`account.key`·`fullchain.pem`·`privkey.pem`, 디렉터리 0700, 파일
  0600)에 둔다. 둘을 가르는 것은 `tls.source` 하나다 — §9.1.
- Cloudflare 토큰: **상태 파일에 넣지 않는다.** DNS-01로 갱신해야 해서
  나중에도 필요할 때만 `/var/lib/anago/cf-token`(0600)에 따로 두고,
  상태에는 그 경로만 적는다 — §9.1.
- 클라: `~/.config/anago/device.json`(도메인·기기 토큰·할당 IP·서버
  공개키), 0600. wg 개인키는 여기 두지 않는다 — wg 설정
  `/etc/wireguard/anago.conf`(wg-quick 규약 위임)에만 있고 기기를
  떠나지 않는다.
  - 정확한 위치는 **`$XDG_CONFIG_HOME/anago/`(설정돼 있고 절대 경로일
    때), 아니면 `$HOME/.config/anago/`**다. `~/.config`는 XDG의 기본값
    이므로, 사용자가 `XDG_CONFIG_HOME`을 옮겨 둔 시스템에서 `~/.config`를
    고집하는 것은 규약 위반이다. 상대 경로 `XDG_CONFIG_HOME`은 무시한다
    — 현재 디렉터리 기준으로 풀면 기기 토큰이 사용자가 서 있던 아무
    곳에나 떨어진다. 둘 다 없으면 추측하지 않고 실패한다.
  - **이 규칙은 "사람이 자기 셸에서 친다"를 전제한다.** 사용자 세션 밖에서
    도는 실행 — M1의 sync 타이머가 유일하다 — 은 환경에 물어보지 않고
    `--config`로 받은 절대 경로를 쓴다. 설치할 때 굽고 유닛에 남긴다(§8).
  - **sudo로 실행된 경우**(`SUDO_UID`가 있으면): 우선순위는 그대로
    **보존된 절대 `XDG_CONFIG_HOME` → `SUDO_UID`의 passwd 홈**이고,
    root의 `HOME`은 쓰지 않는다. 이유는 왕복이다 — 파일은
    `sudo anago join`이 쓰고 평범한 `anago ls`가 읽으므로 두 실행이 같은
    경로를 골라야 한다. sudo는 기본적으로 `XDG_CONFIG_HOME`을 지우므로
    XDG를 옮겨 쓰는 사람은 `sudo -E`가 필요하고, 그렇지 않은 경우
    passwd 홈이 평범한 실행과 같은 답을 준다. root의 `HOME`을 따르면
    `/root/.config/anago`에 쓰여 정작 본인이 찾지 못한다.
  - 소유권도 같이 넘긴다: 파일은 **그것을 만든 디스크립터에 `fchown`**
    으로 `SUDO_UID`/`SUDO_GID`의 것이 된다(경로 기반 `chown`은 그 사이
    이름이 심볼릭 링크로 바뀌는 경합이 있다). 디렉터리는 **anago가 만들지
    않는다** — root가 사용자 소유 경로에 `mkdir -p`를 하는 것 자체가
    링크를 통한 권한 적용 통로다. 없으면 사람에게 만들라고 안내하고
    멈춘다.
  - 서버 쪽 경로에는 이런 재정의가 없다. `/var/lib/anago/`는 systemd
    유닛이 가리키는 고정 위치이고 root 소유다.

### 9.1 서버 상태 파일 스키마

`version`은 **M1에서 2로 올린다**(M0가 쓴 파일은 1). 읽을 때 규칙은
셋이다:

- `2`: 그대로 읽는다.
- `1`: **인메모리로 승격해 읽는다** — 손실 없는 변환이다(아래 "v1 → v2").
- 그 밖(0, 3 이상, 없음, 정수가 아님): **에러로 중단**한다. 구버전
  바이너리가 신버전 상태를 덮어쓰는 사고를 막는 M0의 규칙 그대로다.

모르는 필드는 무시한다. 시각은 전부 **Unix epoch 초(정수)** — 미니
JSON에 날짜 파싱을 들이지 않기 위해서다.

```json
{
  "version": 2,
  "domain": "net.example.com",
  "subnet": "10.100.0.0/24",
  "listen_port": 51820,
  "api_port": 443,
  "tls": {
    "source": "acme",
    "cert_path": "/var/lib/anago/tls/fullchain.pem",
    "key_path": "/var/lib/anago/tls/privkey.pem",
    "not_after": 1763276000,
    "acme": {
      "directory": "https://acme-v02.api.letsencrypt.org/directory",
      "contact": "jo@example.com",
      "account_key_path": "/var/lib/anago/tls/account.key",
      "account_url": "https://acme-v02.api.letsencrypt.org/acme/acct/1234",
      "challenge": "http-01",
      "issued_at": 1755500000,
      "renew_after": 1760684000
    }
  },
  "cloudflare": {
    "zone_id": "023e105f4ecef8ad9ca31a8372d0c353",
    "record_id": "372e67954025e0ba6aaa6d586b9e0b59",
    "token_path": "/var/lib/anago/cf-token"
  },
  "server": {
    "private_key": "<wg base64>",
    "public_key": "<wg base64>",
    "address": "10.100.0.1"
  },
  "peers": [
    {
      "name": "macbook",
      "public_key": "<wg base64>",
      "address": "10.100.0.2",
      "token_hash": "<토큰의 SHA-256, hex 64자>",
      "created_at": 1755500000,
      "last_seen": 1755500600
    }
  ],
  "codes": [
    {
      "code": "7QX4-M2KD",
      "issued_at": 1755499000,
      "expires_at": 1755499900,
      "used_at": null
    }
  ]
}
```

| 필드 | 타입 | 의미 |
|---|---|---|
| `version` | 정수 | 스키마 버전. M0 = 1, M1 = 2. 1은 승격해 읽고, 그 밖은 에러 |
| `domain` | 문자열 | `server init --domain` 값. 클라 엔드포인트 조립에 사용 |
| `subnet` | 문자열 | CIDR. /24만 허용한다 |
| `listen_port` | 정수 | wg UDP 포트(기본 51820) |
| `api_port` | 정수 | 컨트롤 API TCP 포트(기본 443) |
| `tls.source` | 문자열 | `"manual"`(사람이 준 인증서) 또는 `"acme"`(anago가 발급·갱신) |
| `tls.cert_path` / `tls.key_path` | 문자열 | 인증서·키 경로. **`source`와 무관하게 항상 채워진다** |
| `tls.not_after` | 정수 \| null | **인증서에 적힌 실제 만료 시각**(epoch 초). 읽지 못했으면 `null` — 아래 |
| `tls.acme` | 객체 \| null | `source`가 `"acme"`일 때만. 아니면 `null` |
| `tls.acme.directory` | 문자열 | ACME 디렉터리 URL. staging과 production을 가르는 것이 이 값이다 |
| `tls.acme.contact` | 문자열 \| null | `--acme-email`. 바뀌면 계정을 새로 만드는 게 아니라 CA에 갱신 요청을 보낸다 — 아래 |
| `tls.acme.account_key_path` | 문자열 | ACME 계정 자격증명 파일 경로(0600) — 아래 |
| `tls.acme.account_url` | 문자열 | 등록된 계정 URL. 표시·진단용이고, CA에 우리를 증명하는 것은 키다 |
| `tls.acme.challenge` | 문자열 | `"http-01"` 또는 `"dns-01"`. 갱신도 같은 방식으로 한다 |
| `tls.acme.issued_at` | 정수 | 인증서를 받은 시각 |
| `tls.acme.renew_after` | 정수 | **이 시각이 지나면 갱신한다.** 만료(`tls.not_after`)가 아니라 정책이다 — 아래 |
| `cloudflare` | 객체 \| null | Cloudflare 토큰으로 DNS를 만진 적이 있으면. 아니면 `null` |
| `cloudflare.zone_id` | 문자열 | 도메인 → zone 조회 결과 캐시 |
| `cloudflare.record_id` | 문자열 \| null | anago가 만든 A 레코드의 id 캐시. 아직 없거나 무효화됐으면 `null` — 아래 |
| `cloudflare.token_path` | 문자열 \| null | DNS-01일 때만 토큰 파일 경로. 아니면 `null` |
| `server.private_key` / `public_key` | 문자열 | 서버 wg 키쌍(`wg genkey`/`wg pubkey` 산출물, base64) |
| `server.address` | 문자열 | 서버 사설 IP = 서브넷의 .1 |
| `peers[]` | 배열 | 등록 기기. 이름은 유일(§8 `rm`의 키) |
| `peers[].token_hash` | 문자열 | 기기 토큰의 SHA-256 해시(hex 64자). 평문은 저장하지 않는다 — §7.1 |
| `peers[].created_at` | 정수 | join 성공 시각 |
| `peers[].last_seen` | 정수 \| null | 마지막 인증된 API 호출 시각. 아직 없으면 null |
| `codes[]` | 배열 | 발급된 조인 코드. 소진·만료된 항목도 감사 목적으로 남긴다 |
| `codes[].used_at` | 정수 \| null | 소진 시각. null이면 미사용 |

**없는 것은 키를 빼지 않고 `null`을 쓴다.** `tls.acme`도
`cloudflare`도 마찬가지다. 출력이 결정적이어야 하고(§10.1), "없다"가
"이 바이너리는 그 필드를 모른다"와 구별되는 편이 낫다.

#### TLS 출처: `manual`과 `acme`

M0의 평평한 `tls_cert_path`/`tls_key_path`를 `tls` 객체로 바꾼다.
**`cert_path`와 `key_path`는 두 경우 모두 채워진다** — TLS를 로드하는
코드는 `source`를 보지 않고, rustls에 먹일 파일 두 개를 그냥 읽는다.
`source`가 가르는 것은 단 하나, **누가 그 파일을 갱신하는가**다.

- `"manual"`: 사람이 `--tls-cert/--tls-key`로 준 경로. anago는 읽기만
  하고 절대 쓰지 않는다. 갱신도 하지 않는다 — certbot이든 무엇이든
  그 파일을 관리하는 쪽이 따로 있다는 뜻이다. M0의 경로가 그대로
  살아 있는 자리이고, M1에서도 1급 시민이다(§11).
- `"acme"`: anago가 발급했고 anago가 갱신한다. 경로는
  `/var/lib/anago/tls/` 아래로 고정된다.

M0가 쓰던 수동 경로는 이렇게 남는다 — 위 예시와 같은 파일의 다른 모습
이다:

```json
  "tls": {
    "source": "manual",
    "cert_path": "/etc/ssl/anago/fullchain.pem",
    "key_path": "/etc/ssl/anago/privkey.pem",
    "not_after": 1763276000,
    "acme": null
  },
```

이 구분이 상태에 남아야 하는 이유는 갱신 루프 때문이다. 파일만 보면
둘을 구별할 수 없고, 남의 인증서를 anago가 덮어쓰는 것은 되돌릴 수
없는 사고다.

#### v1 → v2 승격

M0 파일에는 `tls_cert_path`/`tls_key_path`가 있고 ACME도 Cloudflare도
없다. 그 상태의 v2 의미는 정확히 하나뿐이라 변환이 전면적이다:

```
tls_cert_path, tls_key_path
  → tls = { source: "manual", cert_path, key_path,
            not_after: null, acme: null }
cloudflare = null
```

`not_after`가 `null`인 것은 승격이 **파일을 읽는 일만** 하기 때문이다 —
인증서를 열어 만료를 뜯어보는 것은 승격의 일이 아니고, 다음에 TLS를
로드할 때 채워진다. 그 밖에는 추측이 들어가는 자리가 없으므로 사람에게
묻지 않고 조용히 승격한다.
다만 **읽는 김에 파일을 고쳐 쓰지는 않는다** — `anago ls`가 상태
파일을 건드리는 것은 놀라운 일이다. 상태를 바꾸는 명령(`code`, join,
`rm`, 인증서 발급)이 저장할 때 자연히 v2로 기록된다.

**다운그레이드는 막힌다.** v2 파일을 M0 바이너리가 열면 위 규칙대로
에러로 멈춘다. 이건 부작용이 아니라 `version`을 둔 목적 그 자체다 —
ACME 정보를 모르는 바이너리가 그 필드를 지운 채 덮어쓰는 것, 그게
막으려던 사고다.

#### 인증서 시각: `not_after`는 사실, `renew_after`는 정책

**두 값을 따로 적는다.** 하나로 합치지 않는 이유는 정하는 주체가 다르기
때문이다.

- **`tls.not_after`** — 인증서에 적힌 실제 만료 시각. CA가 정하고
  우리는 읽기만 한다. `"manual"` 인증서에도 채운다(anago가 갱신하지는
  않지만 만료일은 보여 줄 수 있어야 한다).
- **`tls.acme.renew_after`** — 이 시각이 지나면 갱신을 시도한다.
  우리가 정하고, 사람이 파일을 열어 앞당길 수도 있다. 발급하는 순간
  계산해 적는다.

**계산식은 고정 일수가 아니라 수명의 비율이다.**

```
renew_after = issued_at + (not_after - issued_at) * 2/3
```

`not_after`를 읽지 못했으면(=`null`) **가장 짧은 수명을 가정한다** —
`issued_at + 30일`. 모를 때 낙관하지 않는다.

고정 일수를 쓰지 않는 이유는 그 상수가 이미 무너지고 있기 때문이다.
Let's Encrypt는 기본 인증서 수명을 90일에서 **64일로, 다시 45일로**
줄이는 전환을 공지했고, 권장 갱신 시점도 "90일의 60일째"에서 "45일의
30일째"로 함께 옮긴다고 밝혔다. 즉 **수명의 약 2/3**만이 변하지 않는
값이고, "60일"은 90일 수명에만 맞는 숫자다 — 45일짜리를 받아 놓고
60일에 갱신하겠다고 적으면 만료 뒤에 깨어나는 계획을 파일에 적는 셈이다.

그래서 `not_after`가 여기서 **안전망이 아니라 입력**이 된다. 안전망
노릇도 여전히 한다: 어떤 이유로든 `renew_after`가 `not_after`를 넘어서
있으면 그 자체가 잘못된 상태이므로, 판정 함수는
`min(renew_after, not_after - 여유)`로 시점을 앞당기고 그 사실을 로그와
`server status`(M3)가 말한다. **여유는 7일이다** — 갱신이 실패하기
시작한 뒤 사람이 알아차리고 손볼 시간으로 잡은 값이고, 어떤 수명에도
`renew_after`(수명의 2/3)보다 뒤에 오지 않는다. 이 안전망이 실제로
작동했다면 계산식이나 인증서 수명 중 하나가 예상 밖이라는 뜻이므로,
조용히 넘기지 않고 말한다.

**`not_after`는 어디서 오는가.** §10.2대로 `x509-parser`는 켜지 않는다
(그건 ARI용이고 ASN.1 파서 계열을 십수 개 끌고 온다). 대신 **바이너리가
이미 있는 `rustls-pemfile`로 PEM을 DER로 풀고, 코어의 순수 함수가 그
DER에서 `notAfter` 한 필드만 읽는다.** 경로는 고정돼 있다:
`Certificate` → `TBSCertificate` → `Validity` → 두 번째 `Time`.
UTCTime과 GeneralizedTime 둘 다 받아 epoch 초로 바꾼다. 체인 파일이면
첫 인증서(엔드 엔티티)를 본다.

이것이 §10.2가 QR 인코더를 코어에서 거절한 것과 어긋나지 않는 이유는
성격이 다르기 때문이다. QR 인코더는 리드-솔로몬·마스킹까지 갖춘 **범용
라이브러리**를 코어에 들이는 일이고, 이쪽은 이미 손에 쥔 바이트에서
**필드 하나를 꺼내는 읽기**다. 무엇보다 **신뢰 판정에 쓰이지 않는다** —
인증서 검증은 rustls가 하고(§7), 이 값은 갱신 일정과 표시에만 쓴다.
그래서 실패해도 안전하다: **읽지 못하면 `not_after`는 `null`이고**,
갱신은 `renew_after`만으로 그대로 돈다. 파싱 버그가 낼 수 있는 최악은
"만료일을 표시하지 못한다"이지 "붙지 못한다"가 아니다.

`renew_after`를 굳이 따로 저장하는 이유도 같은 결이다. 규칙은 앞으로도
바뀐다 — 수명 전환이 다음 단계로 넘어가거나 ARI(RFC 9773)를 켜게 되면,
그때 바뀌는 것은 `renew_after`를 **계산하는 코드**뿐이고 스키마도 이미
발급된 허브의 예정 시각도 흔들리지 않는다. 값이 아니라 결정을 적어 두면
전환기에도 이미 선 허브가 조용히 틀려 있지 않는다.

#### ACME 계정: 파일 하나와 재사용 규칙

`account_key_path`가 가리키는 파일에는 **계정 키만이 아니라
`instant-acme`의 계정 자격증명 한 덩어리**(JSON: 키(base64 DER), 계정
id, 디렉터리 URL)가 들어간다. 키만 따로 저장하는 쪽이 이름과는 더
맞지만, 라이브러리가 계정을 복원하는 경로가 이 덩어리 하나를 받는
것이고, 쪼개 두면 복원할 때 라이브러리가 이미 갖고 있는 것을 우리가
다시 조립하게 된다. 파일은 다른 비밀과 같은 규칙으로 쓴다 — `tls/`는
0700, 파일은 0600, 원자적 교체(§7.1).

계정은 **재사용이 기본**이다. CA는 새 계정 수를 세고, 갱신마다 계정을
만드는 구성은 1년을 잘 돌다가 인증서가 만료되는 날 레이트 리밋을
만난다(§13). 재등록을 강제하는 것은 셋뿐이고 전부 취향이 아니라 사실
이다:

- 기록된 계정이 아예 없다(첫 실행, 또는 수동→ACME 전환).
- 기록된 계정이 **다른 디렉터리**의 것이다. ACME 계정은 CA 하나에만
  존재하므로 staging→production 전환은 등록을 다시 해야 한다.
- **키 파일이 없다.** CA에게 그 계정이 우리 것임을 증명하는 것이 키라,
  키가 없으면 기록된 URL은 대답할 수 없는 이름이다.

`--acme-email`이 바뀐 것은 여기 없다. 같은 계정에 새 주소를 알리면
되고(ACME 계정 업데이트), 이메일 하나 바꾸자고 계정을 버리는 것은
레이트 리밋을 이상하게 쓰는 일이다. 다만 **상태만 바꾸고 CA에 알리지
않는 것도 답이 아니다** — 만료 경고가 아무도 안 보는 주소로 간다.

**새 자격증명은 발급이 끝난 뒤에 쓴다.** 등록은 주문보다 먼저 일어나야
하지만(주문에 계정이 필요하다), 파일을 먼저 갈아 끼우면 그 파일이 갖고
있던 **이전 계정 키의 유일한 사본**이 사라진다. staging→production
전환에서 등록 직후에 쓰고 주문이 실패하면, 상태는 설계대로 staging에
남는데(§8, 전부-아니면-전무) 파일에는 staging 계정이 없다 — 되돌릴 수
없는 상태다. 그래서 등록 결과는 메모리에 들고 있다가 **인증서를 손에
쥔 커밋 시점에만** 파일을 교체한다. 순서는 **자격증명 먼저, 상태 파일
나중**이다. 둘은 한 번의 원자적 쓰기가 아니므로 한쪽이 먼저 착지하는데,
이 순서면 새로 등록한 계정이 디스크에 남고 상태가 옛 계정을 가리키는
어긋남은 다음 실행이 아래 검사로 **시끄럽게** 잡는다.

**재사용 전에 파일이 그 계정인지 확인한다.** `from_credentials`는
JSON에 박혀 있는 디렉터리 URL로 접속한다 — 우리가 들고 다니는
`directory` 인자는 보지 않는다. 즉 **어느 CA에 접속하는지는 인자가
아니라 파일이 정한다.** 백업을 잘못 되돌렸거나, 다른 허브에서 복사됐거나,
위 전환이 중간에 끊긴 파일이면 `--acme-staging`을 쳤는데 프로덕션에서
받아 오거나 — 더 나쁘게 — 상태는 신뢰된다고 적힌 채 신뢰되지 않는
인증서를 서비스하게 된다(§13). 그래서 쓰기 전에 파일의 `directory`와
계정 id를 상태와 대조하고, 어긋나면 **고치지 않고 거부한다**. 위에
새로 등록해 버리면 그 파일이 무엇이었든 — 남의 허브 계정일 수도 있다 —
키보드 앞의 실수 하나를 복구하려고 지우는 셈이다. 메시지가 두 길(올바른
파일 복원, 또는 지우고 새로 등록)을 알려 준다.

**약관 동의(RFC 8555 §7.3.1)는 등록할 때 참으로 보낸다.** 사람이
`--acme-email`을 주고 발급을 시킨 것이 그 CA에서 인증서를 받겠다는
지시이기 때문이다. CA의 약관 URL은 디렉터리 메타데이터에 있고, init
출력이 그것을 가리킨다.

#### HTTP-01: :80 임시 리스너와 발급물 저장

챌린지에 답하는 리스너는 **발급 구간에만 뜨고 끝나면 포트를 돌려준다.**
서비스하는 것은 `/.well-known/acme-challenge/<token>` 하나뿐이고, 기다리지
않는 토큰에는 404를 준다 — 빈 200은 CA가 "틀린 답"으로 읽고, 로그에서도
거짓말이 된다. 잠깐 :80에 있는 허브가 웹서버처럼 굴 이유는 없다.

- **IPv6와 IPv4를 각각의 소켓으로 잡고, 둘 다 필요하다.** 어느 쪽으로
  가져갈지는 CA가 정하고, 이름에 AAAA가 있으면 IPv6로 온다. IPv6 소켓은
  `IPV6_V6ONLY`로 연다 — 이 옵션이 없으면 "IPv6를 잡았다"와 "IPv6와
  IPv4를 잡았다"가 **같은 호출**이 되고, 그러면 남의 프로세스가 한쪽을
  쥐고 있는 상황과 듀얼스택 소켓이 양쪽을 덮는 상황을 구분할 수 없다.
  구분하지 못하면 한쪽만 뜬 채로 성공을 보고하고, CA 요청은 그 남의
  프로세스가 받아 검증이 실패한다. std는 이 옵션을 설정할 수단이 없으므로
  libc로 소켓을 직접 만든다(이미 flock·fchown으로 쓰고 있는 의존성이다).
  비어 있어도 되는 유일한 경우는 **그 호스트에 그 주소군이 아예 없을
  때**다(`EAFNOSUPPORT`·`EADDRNOTAVAIL` 등) — IPv4 전용 VPS는 평범한
  VPS이고, 그건 막힌 게 아니라 없는 것이다.
- **바인드 실패는 두 가지로 갈라 말한다.** 권한이면 root/CAP_NET_BIND_SERVICE
  와 함께 "DNS-01은 포트가 아예 필요 없다"를, 사용 중이면 웹서버(nginx 등)를
  잠깐 멈추라는 것과 **필요한 시간이 초 단위**라는 것을 말한다 — 후자를
  빼면 "anago가 :80을 영원히 원한다"로 읽혀 그것만으로 포기할 이유가 된다.
- **검증 실패 메시지는 CA가 가져가려던 URL을 그대로 싣는다.** 다른 기계에서
  `curl`로 같은 실패를 재현할 수 있는 한 줄이고, 열려야 하는 곳이 호스트
  방화벽만이 아니라 클라우드 보안그룹이라는 것도 함께 말한다.
- **기다림에는 상한이 있다**(90초). :80이 끝내 안 열리는 허브에서 `init`이
  영원히 매달리면 안 되고, 사람이 읽을 수 있는 실패로 끝나야 한다(§13).
- **인증서와 키는 한 쌍으로 게시한다.** 둘은 파일 두 개에 나뉜 하나이고,
  반쪽만 새것이면 허브가 안 뜬다. 순서는 이렇다: ① 새 파일 둘을 임시
  경로에 쓰고 fsync한다 ② 기존 첫 파일을 **백업 형제 파일로 복사**한다
  ③ 그다음에야 rename 둘. 디스크가 차거나 경로가 안 써지는 평범한 I/O
  실패는 전부 ①②에서 걸려 "아무 일도 없었다"로 끝난다.
  - **기존 파일을 읽지 못하면 게시 전에 멈춘다.** 사본이 없으면 되돌릴
    수 없고, 그걸 게시 후에 알게 되는 건 늦다.
  - 둘째 rename이 실패하면 첫 파일을 되돌린다 — 기존 파일이 있었으면
    **백업을 rename**해서(다시 쓰는 게 아니라서 도중에 디스크가 차지
    않는다), 없었으면(첫 발급) **지운다**. 키만 홀로 남는 것도 같은
    불일치의 다른 모양이다.
  - **되돌리기가 실패하면 그것까지 보고한다.** 디스크에 안 맞는 쌍이
    있는데 "아무 일도 없었다"고 말하는 에러가 제일 나쁘다.
  - 남는 것은 두 rename 사이에서 기계가 죽는 창 하나뿐이고, 마이크로초
    단위이며 결과가 기동 시점에 드러난다(복구는 `server renew --force`).
    키를 먼저 쓰는 이유는 그 창에서 공개 절반이 결코 더 새것이 되지
    않게 해서 어긋남의 방향을 늘 같게 하기 위해서다.
- **리스너는 CA가 확인한 직후 내린다.** 소유 증명이 끝나면(`Ready`)
  토큰을 다시 가져갈 일이 없고, 그 뒤의 finalize와 인증서 수령 폴링은
  1분 반이 더 걸릴 수 있다. 그동안 :80을 쥐고 있으면 "웹서버를 몇 초만
  멈춰 달라"고 해 놓고 다른 걸 하는 셈이다.
- **취소돼도 포트는 돌아온다.** `JoinHandle`은 그냥 버리면 detach되므로,
  상위 future가 타임아웃·abort·패닉으로 취소되면 서버 태스크가 런타임에
  남아 :80을 계속 쥔다. 그래서 `Drop`에서 abort하고, 정상 경로의
  `stop()`은 거기에 더해 **기다린다** — 반환 시점에 소켓이 닫혀 있음을
  약속하는 것은 `stop()`뿐이다.

#### DNS-01: TXT 챌린지와 폴백하지 않는다는 규칙

흐름은 HTTP-01과 같고 리스너 자리에 TXT 레코드가 들어가며, 한 단계가
더 있다 — **레코드가 실제로 응답될 때까지 기다린 뒤에** CA에 확인을
요청한다(`dnsprobe`). 너무 일찍 부르면 CA는 아무것도 못 보고, 그
실패는 레이트 리밋이 세는 "인증 증명 실패"를 하나 먹는다(§13).

- **정리는 조건부가 아니다.** 발행된 레코드는 스스로를 지우는 가드가
  들고 있어, 오류·조기 반환·패닉 어느 쪽으로 나가도 함께 사라진다(§9.1).
  정상 경로에서는 **검증 직후 명시적으로 지운다** — HTTP-01 리스너를
  그때 내리는 것과 같은 이유이고, 지웠는지 아닌지를 보고할 수 있다는
  차이가 있다.
- **전파 대기는 런타임 밖에서 돈다.** `dnsprobe`는 UDP 소켓과 sleep을
  쓰는 평범한 블로킹 코드라, async 위에서 그냥 부르면 그 스레드를 최대
  1분 묶는다.
- **검증 실패는 DNS의 말로 진단한다.** 실패 메시지는 챌린지 종류를 알고
  갈라진다 — HTTP-01은 CA가 가져가려던 URL과 포트·방화벽·보안그룹을,
  DNS-01은 **TXT 이름과 어느 zone이 실제로 그 이름에 답하는지**(위임된
  서브존은 스스로 답한다), 낡은 레코드가 남아 있는지, 토큰이 그 zone을
  고칠 수 있는지를 짚는다. DNS-01 진단에는 포트 이야기가 한 줄도
  없다: :80을 닫아 두려고 DNS-01을 고른 사람에게 포트를 열라고 하는
  것은 두 번 틀린 안내이고(DNS 문제는 그렇게 안 고쳐진다), 포트가
  등장하는 곳은 아래 "전환하지 않는다" 문단이 http-01의 **대가**를
  말할 때뿐이다.
- **못 본 채 진행한 대기는 성공 옆에 경고로 붙는다.** blind는 실패가
  아니다(인증서는 진짜다) — 다만 "응답되는 것을 확인했다"와 "그러길
  바랐다"의 차이이고, 그 차이는 사람이 판단할 몫이다.

**그리고 DNS-01이 실패해도 HTTP-01로 자동 전환하지 않는다.** 이것이
§8의 폴백 규칙이 실제로 갈리는 지점이다.

- **A 레코드**는 실패하면 M0 수동 안내로 폴백한다. 거기서 토큰이 하는
  일은 사람이 브라우저에서 10초면 하는 일이고, 안내가 그대로 밑에
  깔려 있다(§6.1).
- **챌린지**는 그렇지 않다. 토큰이 편의가 아니라 메커니즘 전부이고,
  더 중요하게는 **두 챌린지의 폭발 반경이 다르다**(§13). DNS-01을 고른
  사람은 :80을 닫아 두려고 골랐을 수 있다 — 그 포트를 여는 것은 호스트
  방화벽, 클라우드 보안그룹, 남이 쓰는 웹서버 중 하나를 건드리는
  일이다. 대신 열어 주고 "성공했습니다"라고 보고하는 것은 anago가 할
  일이 아니다. 그래서 멈추고, **http-01을 사람이 고를 선택지로 알려
  준다**(`--acme-challenge http-01`, 그 대가와 함께).

#### 갱신 루프: 언제 보고, 실패하면 얼마나 벌리는가

허브 데몬(`server run`) 안에서 **한 시간에 한 번** 상태를 다시 읽고
`renew_after`/`not_after`로 판정한다(§9.1의 갱신 규칙). 한 시간인 이유는
갱신 창이 며칠 단위라 그보다 자주 볼 필요가 없어서가 아니라, **사람이
손으로 바꾼 인증서나 `server renew`를 그 안에 알아채기** 위해서다. 판정은
순수 함수이고 잠드는 시간도 그렇다 — 다음 갱신이 한 시간 안이면 그때까지만
자고, 아무리 멀어도 한 시간을 넘겨 자지 않는다.

실패했을 때 간격을 벌리는 정책은 **CA의 예산 계산**이지 예의가 아니다.

- **15분에서 두 배씩, 최대 24시간.** Let's Encrypt는 실패한 검증을
  계정·호스트명·**시간당**으로 센다(§13). 1분마다 재시도하면 5분 만에
  그 예산을 다 쓰고, 정작 문제가 고쳐졌을 그 한 시간 동안 잠긴다.
  15분에서 두 배씩이면 첫 한 시간에 3번이고 그 뒤로는 더 드물다.
- **CA가 레이트 리밋이라고 말하면 바닥이 1시간이다.** LE의 리밋은 시간
  단위로 회복되므로(§13) 15분부터 기어 올라가는 것은 이미 들은 답을
  다시 확인하는 데 시도를 몇 번 쓰는 일이고, 그 시도 하나하나가 이미
  가득 찬 리밋에 또 쌓인다. 리밋 여부는 CA의 problem 문서(에러 텍스트)로
  판정한다 — `instant-acme`이 `Retry-After` 헤더를 따로 주지 않는다.
- **`Retry-After`는 절대 깎지 않는다.** 상한(24시간)보다 길어도 그대로
  따른다. 그걸 무시하는 것이 임시 제한을 더 긴 제한으로 만드는 길이다.
- **상태 파일을 못 읽는 것은 "갱신할 게 없다"가 아니다.** 읽기 실패를
  수동 인증서와 같이 취급하면 한 시간씩 조용히 자다가 인증서가 만료된다.
  읽기 오류는 **말하고**, 별도의 백오프로 다시 시도한다 — CA 실패와 다른
  문제이므로 카운터도 따로 둔다(한쪽이 다른 쪽을 늦추면 안 된다).
- **기다림은 두 종류이고, 지우는 조건이 다르다.**
  - **anago의 지수 백오프**는 CA의 *실패한 검증* 예산을 지키려고 있는
    것이고, 그 예산은 **계정·호스트명·CA**로 센다(§13) — 챌린지로 세지
    않는다. 그래서 HTTP-01로 네 번 실패한 뒤 `--acme-challenge dns-01`로
    고쳐도 **쓴 시도는 쓴 것이다**: 카운터와 대기를 그대로 들고 간다.
    잊어버리면 다섯 번째가 즉시 나가고 백오프가 15분부터 다시 시작해,
    이 장치가 지키려던 시간당 한도를 그 장치가 넘긴다.
    되돌리는 것은 **다른 예산이라는 근거**가 있을 때뿐이다:
    - **다른 계정이나 다른 CA** — 방금 등록한 계정은 아직 아무것도 쓰지
      않았고, staging과 production은 따로 센다.
    - **인증서가 어디선가 새로 왔다**(`issued_at`이 움직였다) — 누가
      했든 성공이고, 실패하던 일은 끝났다. 이때는 CA가 부과한 대기까지
      함께 푼다: 발급해 준 CA가 리밋이 막고 있지 않다고 말한 셈이다.
    - 그 밖의 변경(챌린지, 연락처, 경로)은 **같은 CA에 같은 이름을 묻는
      같은 요청**이므로 아무것도 되돌리지 않는다.
  - **CA가 부과한 대기**(레이트 리밋 바닥, `Retry-After`)는 그렇지
    않다. **우리가 설정을 바꾼다고 CA의 마음이 바뀌지는 않는다.** 리밋은
    계정·호스트명·CA로 세지 챌린지로 세지 않으므로(§13), HTTP-01에서
    리밋을 맞고 `--acme-challenge dns-01`로 고친 허브는 같은 CA에 같은
    이름을 다시 묻는 같은 허브다. 여기서 대기를 지우면 "사흘 뒤에
    오라"는 지시가 다음 정시 점검의 새 주문이 되고, 임시 제한이 더 긴
    제한이 된다. 그래서 이 대기는 **발급이 성공했거나 디렉터리(CA)가
    실제로 달라졌을 때만** 풀린다 — staging과 production은 리밋을 따로
    세므로 그 이동은 진짜로 다른 통이다. 같은 이유로 **두 번째 실패가
    이미 선 대기를 줄이지도 못한다.**
- **성공만 카운터를 되돌린다.** 재시작도 되돌린다 — 실패 횟수를 메모리에만
  두기 때문이고, 이건 아는 구멍이다. 상태 파일에 적으면 문제가 사라진
  뒤에도 살아남아 잘 됐을 갱신을 늦춘다. 갱신이 깨진 허브를 사람이 계속
  재시작하는 경우 의도보다 자주 시도하게 되는 대가는 감수한다.
- **실패해도 서비스는 안 멈춘다.** 디스크의 인증서는 만료 전까지 그대로
  일하고, 출력이 그 사실과 다음 시도 시각을 함께 말한다 — 안 그러면 한
  시간의 침묵이 멈춤처럼 보인다.
- **`Retry-After`는 문자열이 아니라 값으로 옮긴다.** 실패는 "무슨 종류
  였는지"와 "CA가 얼마를 기다리라고 했는지"를 함께 들고 루프까지 온다.
  `to_string()`으로 뭉개면 사흘을 기다리라는 지시가 한 시간 뒤 재시도로
  바뀐다. `instant-acme`이 헤더를 직접 주지는 않지만 폴링 타임아웃은
  "다음에 와도 되는 시각"을 갖고 있어, 그 값이 그대로 백오프의 바닥이
  된다.

**발급 전체는 하나의 잠금으로 직렬화한다.** 타이머와 손으로 친
`server renew`가 겹치는 것은 이상한 일이 아니고, 겹치면 둘이 **같은 계정
파일과 같은 인증서 쌍**에 쓰고 진 쪽이 이긴 쪽이 이미 바꿔 놓은 설정에
자기 결과를 기록한다 — 수동 TLS 허브의 `cert_path`가 anago 파일을 가리키게
되거나, 한 CA의 계정과 다른 CA의 주문이 섞인다. 그래서 **상태를 읽기
전부터** 전용 잠금(`/var/lib/anago/issue.lock`)을 잡는다. 상태 잠금이
아닌 별도 파일인 이유는 발급이 분 단위라서다 — 그동안 join이 전부 막히면
안 된다. 잠금은 **기다리지 않고 시도만** 한다: 사람이 이미 갱신 중이면
타이머가 2분 줄 서서 보탤 것이 없다.

커밋 직전에 **발급을 시작할 때의 TLS 설정이 그대로인지** 확인하고, 달라졌
으면 아무것도 기록하지 않는다. 그 사이에 바뀌었다면 지금 손에 든 인증서는
더 이상 존재하지 않는 허브의 것이다.

**갱신된 인증서는 재시작 없이 리스너에 들어간다.** 설정을 시작할 때 한 번
만들어 붙잡고 있으면 갱신은 의미가 없다 — 사람이 프로세스를 다시 띄울
때까지 만료된 인증서를 계속 내민다. 그래서 리스너는 핸드셰이크마다 읽는
핸들(`axum-server`의 `RustlsConfig`)을 들고, 갱신 커밋 뒤 그 핸들을
교체한다. 이미 열린 연결은 그대로 살아 있고, **다음 연결부터** 새
인증서를 받는다.

교체 시점은 커밋 **뒤**다. 순서는 ① 계정 자격증명 ② 인증서·키 쌍
③ **새 쌍을 파일에서 다시 읽어 검증** ④ 상태 파일 ⑤ 리스너 교체.
상태 파일이 동의하기 전에 리스너만 바꾸면 재시작 한 번으로 옛 쌍으로
되돌아가는 허브가 된다. 파일을 다시 읽는 이유는 허브가 내미는 것이 디스크에
있는 것과 같아야 하기 때문이고, 그 읽기가 **커밋보다 앞**인 이유는 더
중요하다 — 커밋 뒤에 읽어서 실패하면 상태에는 `renew_after`가 미래로
적혀 있고 리스너는 옛 인증서를 계속 내미는데, 다음 점검은 "아직 아님"만
보고 재발급도 재로딩도 하지 않는다. **묻힌 채 만료된다.** 순서를 이렇게
두면 커밋 뒤에 남는 동작은 실패할 수 없는 핸들 교체 하나뿐이다.

**anago가 발급하지 않은 인증서도 리스너에 들어간다.** 위 순서는 anago가
자기 손으로 받은 인증서 이야기다. 파일이 바뀌는 길은 그것만이 아니다.

- 수동 TLS 허브(M0의 `--tls-cert/key`)에서 certbot이나 acme.sh가 6주마다
  같은 경로를 다시 쓴다. 점검은 `NotOurs`라 발급할 것이 없다.
- 사람이 `server renew`를 직접 친다. 그쪽이 발급 잠금을 쥐므로 상주
  프로세스의 시도는 "지금 누가 갱신 중"으로 끝나고 결과를 못 본다.

둘 다 **디스크의 인증서는 새것인데 리스너는 옛것을 내미는** 상태로 끝나고,
그 상태는 재시작 전까지 안 풀린다. 제때 갱신된 기계에서 만료된 인증서가
나오는 사고가 정확히 이 모양이다. 그래서 갱신 루프는 **매 틱, 판정보다
먼저** 상태가 가리키는 인증서·키를 읽어 리스너가 내밀고 있는 것과 대조한다
— `NotOurs`인 허브에서도 돈다. 발급할 게 없는 허브가 바로 남이 갱신해 주는
허브다.

판정은 순수 함수(`tls::reload`)이고 셋 중 하나다.

- **같다** — 아무것도 안 한다. 인증서는 90일을 사는데 점검은 한 시간마다
  이므로 거의 항상 이 답이고, anago 자신의 갱신 **직후에도** 이 답이다
  (⑤에서 이미 검증한 쌍을 넣었다). 교체가 두 번 일어나지 않는다는 뜻이자,
  갱신이 리스너까지 실제로 닿았다는 확인이기도 하다.

  이 답이 참이려면 **핸들과 "지금 내밀고 있는 체인"이 같이 움직여야
  한다.** ⑤가 핸들만 바꾸고 기준 체인을 안 고치면 두 가지가 어긋난다 —
  바로 다음 점검이 방금 넣은 인증서를 "다름"으로 보고 한 번 더 넣고,
  그 사이 파일이 **이전 체인으로 되돌아오면** 기준과 같으니 "같음"이
  되어 리스너는 디스크에 없는 인증서를 계속 내미는데 그걸 알아챌 점검이
  더는 없다. 그래서 둘은 한 값(`tls::Listening`)이 **같은 잠금 아래**
  들고 있고, 교체하는 경로는 그 둘을 함께 바꾸는 것 하나뿐이다. 지켜야
  할 규칙이 아니라 못 어기는 구조로 둔다.
- **다르다, 그리고 읽힌다** — 교체한다.
- **읽히지 않는다** — **옛 인증서를 그대로 내밀고** 한 줄 남긴 뒤 다음
  점검을 기다린다. certbot은 `fullchain.pem`과 `privkey.pem`을 두 번에
  나눠 쓰므로 그 사이에 걸린 점검은 키와 안 맞는 인증서를 본다. 60일에
  한 번, 1초짜리 창이다. 그걸로 동작 중인 리스너를 내리면 갱신이 장애가
  된다 — 디스크가 뭐가 됐든 지금 내밀고 있는 인증서는 아직 유효하다.

**대조는 파일이 아니라 체인으로 한다.** 클라이언트가 보는 것이 체인이기
때문이다. 경로만 바뀌고 내용이 같으면 교체할 것이 없고, 같은 경로를
60일마다 다시 쓰는 certbot은 교체할 것이 전부 있다. **잎(leaf)이 아니라
체인 전체**를 순서까지 비교한다 — CA가 교차서명하는 중간 인증서를 바꾸면
같은 잎이 다른 체인으로 재발급되고, 그걸 "안 바뀜"으로 넘긴 허브는 경로를
못 만드는 체인을 계속 내민다.

#### Cloudflare 캐시: `zone_id`와 `record_id`

`zone_id`(도메인이 사는 zone)와 `record_id`(anago가 만든 A 레코드)를
캐시한다. 캐시는 조용히 낡을 수 있으므로 규칙을 못박는다.

- **생성**: zone은 도메인에서 찾은 직후 `zone_id`에, A 레코드는 만들거나
  고친 직후 응답이 준 id를 `record_id`에 적는다.
- **조회**: 캐시가 있어도 **upsert 전 레코드 목록 조회를 건너뛰지
  않는다.** 프록시(주황 구름)가 켜졌는지 봐야 하고(§13) 값이 이미
  맞는지도 봐야 한다. 그러니까 `record_id`가 하는 일은 왕복을 줄이는 게
  아니라 **어느 레코드가 우리 것인지 지목하는 것**이다. `zone_id`는
  TXT를 쓰는 데 필요한 것을 이미 갖고 있다는 뜻이지만, **DNS-01 갱신은
  그것만으로 끝나지 않는다** — 전파 확인이 zone의 **네임서버**를 알아야
  하고 그건 상태에 없다. 그래서 갱신 때 zone을 한 번 조회하고, 캐시된
  id는 대조에 쓴다(도메인이 다른 zone으로 옮겨 갔으면 조회 쪽이 맞다).
  6주에 한 번 요청 한둘의 값으로, 레코드를 써 놓고 그게 응답되는지
  볼 수 없는 갱신을 피한다. **조회 결과가 캐시와 다르면 갱신 커밋에서
  새 id를 써 넣는다**(그리고 `record_id`는 함께 버린다 — 다른 zone의
  레코드 id는 의미가 없다). 안 그러면 같은 경고와 같은 재조회가 갱신마다
  영원히 반복되고, 캐시가 상태를 설명한다는 말이 거짓이 된다.
- **이름에 A 레코드가 둘 이상이면 고치지 않고 멈춘다.** 같은 이름에 A를
  여럿 두면 이름이 라운드로빈으로 풀리는데, 허브는 한 대다(§5) — 절반의
  응답이 엉뚱한 주소를 가리키는 상태에서 우리 것 하나를 갱신해 봐야
  "HTTPS가 됐다 안 됐다 하는" 망가진 네트워크를 유지할 뿐이고, 그 사이
  init은 "A 레코드를 갱신했습니다"라고 초록으로 보고한다. §13이 프록시
  항목에서 경계한 모양 그대로다. 사람이 지워야 하는 상태이므로 **무엇이
  있고 그중 어느 것이 우리 것인지 짚어서 알리고 멈춘다** — 캐시가 값을
  하는 자리가 여기다. 이름에 A가 **하나**뿐이면, 그것이 우리가 만든
  것이든(캐시 적중) 사람이 M0의 수동 안내를 따라 만든 것이든(캐시 없음)
  그 레코드를 갱신한다. 후자는 "인계받았다"고 말해 준다.
- **갱신은 `content` 하나만 바꾼다**(`PATCH`). 레코드 전체를 덮어쓰면
  (`PUT`) 인계받은 레코드에 사람이 정해 둔 TTL·주석·태그가 anago의
  기본값으로 조용히 리셋된다 — 인계는 주소를 바꾸는 것이지 레코드를 다시
  만드는 게 아니다. `proxied`도 갱신 본문에 넣지 않는다: 프록시를 끄는
  것 역시 anago가 정할 일이 아니고(§13), 켜진 레코드는 여기 오기 전에
  이미 거부된다. 우리가 값을 정하는 것은 **만들 때**뿐이다 —
  `proxied=false`와 TTL 자동(`1`).
- **목록이 한 페이지를 넘으면 판정하지 않는다.** 다음 페이지에 이름을
  모호하게 만드는 두 번째 A 레코드가 있을 수 있다. 잘린 목록으로 내린
  "하나뿐이다"는 판정은 위 라운드로빈을 그대로 통과시키면서 성공을
  보고한다. 이름으로 걸러 받은 목록도 **로컬에서 이름을 한 번 더
  대조한다** — 어느 레코드가 우리 것인지를 질의 파라미터의 매칭 방식에
  맡기지 않는다. 질의는 현행 API가 문서화한 정확 일치 필터
  (`name.exact`)로 보낸다.
- **도메인은 ASCII(punycode) 철자를 요구하고, 비-ASCII 이름은 거부한다.**
  Cloudflare는 레코드 이름을 punycode로 받고 punycode로 돌려준다. UTF-8로
  보내면 두 번 어긋난다 — 쓰기가 거부될 수 있고, 이미 있는 레코드가
  `xn--…`로 돌아와 로컬 이름 대조에서 탈락해 "없다"로 판정된다. 그러면
  이미 있는 레코드 **옆에** 하나를 더 만들고, 그게 위에서 거부하는
  라운드로빈이다. 그렇다고 anago가 변환하지는 않는다: IDNA는 punycode
  하나가 아니라 매핑·정규화·bidi 규칙이고(§8.1의 정규화 한계와 같은
  결이다), 미묘하게 틀린 변환은 아무도 치지 않는 이름에 레코드를 걸어
  둔다. `xn--` 철자는 대시보드가 이름 옆에 보여 주고 TLS·`Host` 헤더도
  그것을 원하므로, 그 철자를 달라고 하고 어디서나 그대로 쓴다.
- **무효화**: 목록에 캐시된 `record_id`가 없으면(사람이 대시보드에서
  지웠다) 그 id는 버린다. **버린다는 것이 "새로 만든다"는 뜻은 아니다**
  — 무엇을 할지는 지금 그 이름에 무엇이 있는지가 정하고, 위 규칙을 그대로
  다시 적용한다: 아무것도 없으면 만들고, A가 하나 있으면 그것을
  인계하고(캐시 없이 만난 레코드와 똑같이 다룬다), 여럿이면 멈춘다.
  캐시를 버렸다는 이유로 이미 있는 레코드 **옆에** 하나를 더 만들면 그게
  바로 위 문단이 거부하는 라운드로빈 상태다. 새 id는 만들거나 고친
  뒤에 적는다. `zone_id`가 바뀌면 — 도메인을 다른 zone으로 옮겼다 —
  `record_id`도 함께 무효화한다. 다른 zone의 레코드 id는 의미가 없다.
- **거부는 무효화가 아니다**: 캐시가 가리키는 레코드가 프록시 켜짐이거나
  A가 아니면 **멈추고 사람에게 알리되 캐시는 유지한다**(§13). 사람이
  고쳐야 하는 상태이지 anago가 지우고 새로 만들 상태가 아니다.

**DNS-01의 TXT 레코드 id는 캐시하지 않는다.** 챌린지마다 만들고 검증
직후 지우는, 수명이 분 단위인 레코드다. 상태에 남기면 정리에 실패했을
때 다음 실행이 지워야 할 유령을 물려받는다 — 이름
(`_acme-challenge.<domain>`)으로 조회해 지우는 쪽이 언제나 옳다.

**정리는 실패 경로에서도 반드시 돈다.** 레코드를 만든 뒤 인증서를 받기
까지는 빠져나갈 길이 여럿이다 — ACME 오류, 전파 대기 타임아웃, 몇 겹
아래의 `?`, 패닉. 그래서 발행된 챌린지는 스스로를 지우는 값
(`Challenge`, `Drop`)으로 들고 다닌다. 정상 경로는 `remove()`가 지우고
오류를 보고하며, `Drop`은 보고할 데가 없으니 stderr에 "이 TXT를 손으로
지워라"만 남기고 넘어간다 — 그 시점엔 이미 실행이 실패하는 중이고
정리 실패는 소식이 아니다. **가드는 삭제가 성공했을 때만 풀린다** —
id를 먼저 빼고 실패하면 레코드는 남아 있는데 `Drop`은 할 일이 없고
"이 레코드를 손으로 지워라"는 경고도 안 나온다. 가드가 존재하는 이유인
바로 그 경로가 조용히 사라지는 것이다. 프로세스가 통째로 죽어 `Drop`
조차 못 돈 경우는 **다음 실행이 발행 전에 쓸어내는 것**으로 받는다.

**단, 쓸어내는 것은 anago가 쓴 레코드뿐이다.** 한 이름에 TXT가 여럿인
것은 충돌이 아니라 DNS-01이 문서화한 정상 상태다 — 와일드카드 주문과
일반 주문을 동시에 검증하면 그렇게 된다(Let's Encrypt 챌린지 문서). 그
이름에 있다는 이유로 지우면 **남의 발급을 중간에 끊는** 것이고, anago는
끊었다는 사실조차 모른다. 그래서 만들 때 Cloudflare 레코드 **주석**에
표식(`anago DNS-01 challenge`)을 남기고, 쓸기는 그 표식이 붙은 TXT만
지운다. 주석을 쓰는 이유는 태그와 달리 모든 요금제에서 쓸 수 있어서다.
표식 없는 TXT는 그대로 둔다: 남겨 두는 대가는 이번 검증을 막지 않는
낡은 레코드 하나이고(ACME 서버는 이름에 있는 TXT 중 **하나라도** 맞으면
통과시킨다), 지우는 대가는 모르는 사람의 발급 실패다. 다만 남은 것이
쌓이면 응답이 커져 Let's Encrypt가 거부하므로, **우리 것을 반드시
지우는 쪽**이 이 규칙의 핵심이다. TXT가 아닌 레코드는 건드리지 않는다.

**표식만으로는 부족하다 — 나이도 봐야 한다.** 표식은 "anago가 썼다"를
증명하지 그 실행이 **그 레코드를 다 썼다**를 증명하지 않는다. 한 zone에
anago 실행이 둘인 것은 이상한 일이 아니다: 갱신 타이머가 도는데 사람이
`server renew`를 치면 그렇게 된다. 표식만 보고 쓸면 뒤의 실행이 앞
실행의 **살아 있는 챌린지**를 지우고 앞의 발급을 실패시킨다 — 남의
인증서를 지키려고 만든 규칙이 남의 인증서를 깨는 것이고, 이번엔 그 남이
우리다. 그래서 만들 때 주석에 **기록 시각**(`at=<epoch>`, 진단용
`pid=`도 함께)을 적고, 쓸기는 **표식이 있고 그 시각이 챌린지 수명(10분)
을 넘긴** 것만 지운다. 1분짜리 대기와 초 단위 검증에 10분은 넉넉하고,
다음 갱신까지 찌꺼기가 살아남지 않을 만큼 짧다. 시각을 읽을 수 없는
주석(사람이 고쳤거나 우리 것이 아니거나)은 건드리지 않는다 — 나이를 알
수 없다는 것은 지울 이유가 아니다. 시각을 `created_on`이 아니라 주석에
적는 이유는 그게 RFC 3339이고 anago에는 그걸 읽을 날짜 라이브러리가
없어서다(§10.2).

**그리고 발급 자체는 잠금으로 직렬화한다.** 위 규칙은 겹쳤을 때
*레코드*를 지키는 것이고, 애초에 한 허브에서 갱신 타이머와 손으로 친
`server renew`가 동시에 주문을 넣을 이유가 없다 — 발급 슬라이스가 상태
파일과 같은 결의 flock을 잡는다(§9). 잠금은 한 호스트 안에서만 유효
하므로, 나이 규칙은 그 바깥(다른 호스트·죽은 프로세스)을 받는다.

**전파 대기: DNS에 직접 묻는다.** "Cloudflare가 레코드를 저장했다"와
"그 이름이 그 값을 응답한다"는 다른 사실이고, DNS-01이 걸린 것은
두 번째다. 컨트롤 플레인 API는 첫 번째까지만 말해 줄 수 있으므로 —
API 목록 조회로 대기하면 아직 응답되지 않는 레코드에 대고 검증을
요청하게 된다 — anago는 **zone의 권한 네임서버에 TXT 질의를 직접
보낸다**(`dnsprobe`).

리졸버 의존성은 두지 않는다. std에는 이름→주소 조회만 있고 TXT를 물을
수단이 없지만, 필요한 것은 리졸버가 아니라 **질문 하나와 답 하나**다.
DNS 메시지 조립·해독은 순수 계산이므로 코어(`anago_core::dnswire`,
순수 std)에 두고 픽스처로 유닛 테스트하며, 소켓과 시계만 바이너리가
갖는다. 재귀도 캐시도 서명 검증도 없다 — 이미 권한이 있다고 알려진
서버에 묻고 온 답을 읽을 뿐이고, 답이 틀려 봐야 검증을 조금 일찍이나
늦게 넘기는 것이 전부다. **진짜 판정은 ACME 서버의 조회가 내린다.**

정책은 순수 함수로 분리해 테스트한다(`look`, `next_step`):

- 질의는 **EDNS(0)로 1232바이트까지** 받겠다고 알린다. 안 그러면 상한이
  512바이트고, 같은 이름에 TXT가 여럿인 정상 상태에서 답이 잘린다.
- **잘린 답에 값이 없는 것은 "없다"가 아니다.** 안 들어온 부분이 바로
  값이 있을 자리다. 잘린 답을 부재로 읽으면 이미 퍼진 레코드를 두고
  1분을 기다린 뒤 실패한다. 그래서 잘림은 `Silent`(못 봤음)로 센다 —
  값이 도착한 부분에 보이면 그건 본 것이다. TCP 재질의는 하지 않는다:
  EDNS(0) 뒤에는 만날 일이 거의 없는 경우이고, 만나더라도 결과는
  "확인하지 못했다"로 끝나지 틀린 답으로 끝나지 않는다.
- 네임서버 이름이 푸는 **주소를 전부 시도한다.** 보통 A와 AAAA가 다
  있고 순서는 이 호스트가 무엇에 닿는지와 무관하다. 첫 주소에서 멈추면
  IPv4 전용 호스트가 IPv4로 잘 답하는 서버에 대고 침묵으로 판정하고,
  전부 침묵이면 "확인하지 못했다"로 끝나므로 **대기가 조용히 아무것도
  확인하지 않게 된다.** 한 서버에 주어지는 예산(2초)을 주소들이 나눠
  쓴다 — HTTP 클라이언트가 듀얼스택 허브에 쓰는 규칙과 같다.
- 각 네임서버의 답은 `Serving`/`NotYet`/`Silent` 셋 중 하나다.
  **답하지 않은 서버는 판정을 붙잡지 않는다** — 침묵은 반대 증거가
  아니라 없는 증거다. 둘 중 하나가 이 호스트에서 막혀 있다고 갱신이
  멈추면 안 되고, 답한 쪽도 같은 zone의 권한 서버다.
- 답한 서버가 **모두** 값을 응답하면 통과, 하나라도 아니면 계속,
  아무도 답하지 않으면 "볼 수 없음"이다.
- **2초 간격**으로 묻는다. 창이 1분이라 백오프는 흔한 경우(몇 초 만에
  퍼진다)의 지연만 늘린다.
- 통과하면 **5초 더**(`SETTLE`) 기다린 뒤 넘긴다. Cloudflare는
  애니캐스트라 여기 답한 인스턴스가 ACME 서버에 답할 인스턴스는
  아니다. 짧은 이유는 이제 추측이 아니라 **관측**이 뒤에 있어서다.
- **보였다는 사실이 만료된 시계를 이긴다.** 찾은 조회가 답이다.
- **잠은 마감을 넘지 않는다.** 창 끝에서 간격은 남은 시간으로 잘린다.
- **"볼 수 없음"에는 훨씬 짧은 마감(10초)을 따로 둔다.** 못 묻는 것과
  물어서 아니라는 답을 듣는 것은 다른 사실이고 끝도 다르다: 아웃바운드
  UDP 53이 막힌 호스트(80·443만 여는 구성은 실재한다)는 창 전체를 아무
  것도 배우지 못한 채 쓰고 나서 **자기 눈이 먼 탓에** 인증서를 실패시킬
  것이다. 그래서 10초 뒤에는 "확인하지 못했다"고 경고하고 그대로
  넘어간다.
- 60초 안에 응답되지 않으면 검증을 요청하지 않고 **레코드를 지우고
  멈춘다** — 실패할 게 뻔한 검증은 ACME 쪽 실패 한도만 축낸다(§13).

#### Cloudflare 토큰은 상태 파일에 없다

토큰은 **DNS-01로 갱신해야 할 때만** `/var/lib/anago/cf-token`(0600)에
남기고, 상태에는 `cloudflare.token_path`만 적는다. A 레코드만 만들고
HTTP-01로 발급했다면 토큰은 `server init`이 끝나는 순간 잊는다 —
`token_path`는 `null`이 된다.

§7.1의 논리를 그대로 적용한 것이다. 없앨 수 있는 비밀은 없앤다. 없앨
수 없을 때도 **상태 파일과는 분리한다**: 상태 파일이 통째로 새는 경로
(백업, 이슈에 붙인 덤프)가 서버 침해보다 흔하다는 것이 §7.1의 전제였고,
그때 DNS 편집 권한을 가진 토큰이 같이 나가지 않는 편이 낫다. 분리하면
토큰 회전도 상태 파일을 건드리지 않고 된다.

#### 아직 없는 것

`endpoint`·`last_handshake` 필드는 **M1에도 없다**. 허브-스포크에서
기기 엔드포인트는 서버가 wg 커널에서 관측하는 값이고(`anago ls`는
`wg show`에서 읽는다), 기기 관측 엔드포인트 보고는 M2의
`/api/v1/endpoint`가 생길 때 스키마와 함께 들어온다. 그때
`version`을 3으로 올린다.

### 9.2 기기 파일 스키마 (클라, M0)

`~/.config/anago/device.json`(§9의 경로 규칙). 0600.

```json
{
  "version": 1,
  "domain": "net.example.com",
  "api_port": 443,
  "name": "macbook",
  "address": "10.100.0.2",
  "subnet": "10.100.0.0/24",
  "token": "<64 hex>",
  "server_public_key": "<wg base64>",
  "server_endpoint": "net.example.com:51820",
  "server_address": "10.100.0.1"
}
```

모든 필드가 필수다. 특히 `api_port`가 없는 파일은 **443으로 가정하지
않고 거부한다** — 이 필드가 생기기 전의 빌드도 `--api-port`를 받았지만
그 값을 저장하지 않았으므로, 없다는 것은 "443"이 아니라 "모른다"는
뜻이다. 복구는 **파일에 `"api_port"`를 손으로 적어 넣는 것 하나**다:
이 파일과 wg 설정이 남아 있는 한 다시 join하는 길은 막혀 있고(§6.2의
중복 가입 방지), 허브에는 이미 같은 이름이 등록돼 있다.

join 응답(§8)에 기기가 접속에 쓴 `api_port`를 더해 담는다 — 기기가
나중에 `ls`/`rm`을 하려면 토큰과 도메인과 **포트**가(서버가
`--api-port`로 초기화됐을 수 있다), wg 설정을 다시 만들려면 나머지가 필요하기 때문이다. **wg
개인키는 여기 없다**: `/etc/wireguard/anago.conf`에만 있고 서버로도
가지 않는다(§6.2). `name`은 서버가 정규화해 돌려준 이름이라 `anago rm`
이 그대로 쓸 수 있다.

### 10.1 직렬화 결정: serde를 쓰지 않는다

**anago의 프로토콜 타입과 서버 상태 파일은 anago-core에 넣은 수제
미니 JSON 인코더/파서(순수 std)로 직렬화한다. serde·serde_json은
쓰지 않는다.**

이유는 하나다. §4 원칙 4와 §8이 "스키마의 원본은 anago-core의 타입"
이라고 못박았는데 core는 순수 std라 serde를 쓸 수 없다. 그러면 남는
선택지는 (a) 타입을 core와 바이너리에 이중으로 두고 손으로 동기화
하거나, (b) 스키마 원본을 바이너리로 옮겨 원칙 4를 깨거나, (c) core
안에서 직렬화까지 끝내는 것뿐이다. (a)는 두 정의가 어긋나는 순간
프로토콜이 조용히 깨지고, (b)는 원본 위치를 뒤집는 설계 변경이다.
(c)를 고른다: 필요한 JSON 표면이 작고(위 스키마 + §8의 4개 타입),
전부 순수 함수라 유닛 테스트가 그대로 게이트가 된다.

미니 JSON의 지원 범위를 좁게 고정한다 — 범용 JSON 라이브러리를
만들 생각이 없다:

- 값: 객체·배열·문자열·정수·불·널. **부동소수는 지원하지 않는다**
  (소수점·지수 표기는 파싱 에러). 스키마에 실수가 필요해지면 이
  문서를 먼저 고친다.
- 정수는 `i64` 하나로 통일한다 — 스키마의 정수는 버전·포트·epoch 초
  뿐이라 i64로 충분하고, 부호 유무로 타입을 나누면 파서만 복잡해진다.
  범위를 넘으면 에러.
- 문자열은 UTF-8, `\u` 이스케이프 디코딩 지원. 출력은 필요한 문자만
  이스케이프.
- 객체의 중복 키는 에러(마지막 값 채택 같은 조용한 처리 금지).
- 출력은 **결정적**이다: 필드는 타입에 선언된 순서로 나간다. 상태
  파일은 사람이 읽고 고칠 수 있게 2칸 들여쓰기, API 응답은 압축 형식.

serde가 다시 논의되는 경우는 하나뿐이다: M1에서 ACME·Cloudflare의
**제3자 JSON 스키마**를 다뤄야 할 때. 그건 남의 스키마이고 바이너리
크레이트에만 필요하므로 이 결정과 충돌하지 않는다. **그 판단은 §10.2
에서 내렸다 — `serde_json`을 바이너리 직접 의존성으로 두고, 제3자
응답에만 쓴다.** anago 자신의 프로토콜·상태가 serde로 넘어가는 일은
없다.

### 10.2 M1 의존성 확정 — ACME·Cloudflare·QR

M1이 새로 들이는 **직접** 의존성은 셋이다: `instant-acme`(ACME),
`serde_json`(제3자 JSON), `qrcodegen`(QR 인코딩).

**셋 다 `crates/anago` 바이너리 크레이트에만 선언한다. anago-core는
M1에서도 외부 크레이트를 한 개도 갖지 않는다.** §4 원칙 4의 선은
마일스톤이 바뀌어도 움직이지 않는다 — 코어가 M1에서 맡는 것도 여전히
순수 함수뿐이다(갱신 시점 판정, 챌린지 문자열 조립, DNS 레코드 upsert
판정, sync 판정, QR 렌더링).

#### ACME — `instant-acme`, 기본 feature는 끈다

```toml
instant-acme = { version = "0.8", default-features = false,
                 features = ["ring", "rcgen", "hyper-rustls"] }
```

- **`default-features = false`는 취향이 아니라 요구사항이다.**
  instant-acme의 기본 feature는 `aws-lc-rs`를 고른다. 그대로 받으면
  위 표의 rustls 결정(ring)이 무너지고, aws-lc-rs가 요구하는 C
  툴체인이 "stock VPS에서 그냥 빌드된다"는 이 프로젝트의 배포 전제를
  깬다. 같은 이유로 rustls를 ring으로 고정했으니 ACME도 같은 백엔드를
  쓴다 — 한 바이너리 안에 암호 백엔드를 두 벌 넣을 이유가 없다.
- **`rcgen`**: 인증서 개인키와 CSR을 만든다. `Order::finalize()`가
  내부에서 키를 생성하고 CSR을 서명해 개인키 PEM을 돌려주므로 우리는
  `rcgen`을 직접 부르지 않는다(직접 의존성이 아니라 feature다). ASN.1
  과 서명을 우리가 짜지 않는 것은 §3·§4 원칙 1 그대로다.
- **`hyper-rustls`**: instant-acme이 자기 HTTP 스택으로 쓴다.
  `HttpClient` 트레이트가 열려 있어 우리 클라이언트를 꽂고 이 feature를
  뺄 수도 있지만, 그러자고 async 어댑터를 손으로 짜는 것은 "어려운
  문제는 위임한다"의 반대 방향이다. hyper·hyper-util은 axum-server
  때문에 어차피 트리에 있다.
  - 부작용 하나는 적어 둔다: 이 feature가 `rustls-platform-verifier`를
    끌고 와서, 한 바이너리 안에 트러스트 루트 경로가 두 벌이 된다(기기
    쪽 `rustls-native-certs`, ACME 쪽 platform-verifier). ACME는 공개
    CA(Let's Encrypt)만 상대하므로 §11의 origin-cert 단서와 무관하고,
    **어느 쪽도 검증을 끄지 않는다**.
- **켜지 않는 것: `x509-parser`·`time`.** 둘은 ARI(RFC 9773)의 갱신
  창을 읽기 위한 것이고, 그 대가로 ASN.1 파서 계열(`x509-parser`,
  `asn1-rs`, `der-parser`, `nom` …)이 따라온다. 이것들은 잠금 파일에는
  이름이 남지만(옵션 의존성이라 해석 그래프에 기록된다) **빌드 트리에는
  들어오지 않는다** — `cargo tree`로 확인했다.
  - 정정: **`time` 크레이트 자체는 feature와 무관하게 들어온다.**
    `rcgen`이 인증서 유효기간을 다루느라 무조건 의존하기 때문이다
    (`time`·`time-core`·`deranged`·`num-conv`·`powerfmt`). feature를
    끄는 것으로 막히는 것은 위 ASN.1 파서 계열이지 `time`이 아니다.
  M1의 갱신 시점은 ARI 없이 정한다 — 그 규칙(무엇을 상태에 적고 언제
  갱신하는가)은 §9.1에서 확정한다. 인증서의 `notAfter`는 상태에 적지만
  (§9.1의 `tls.not_after`) 그것 때문에 이 feature를 켜지는 않는다:
  PEM→DER은 이미 있는 `rustls-pemfile`이 하고, DER에서 그 필드 하나를
  읽는 것은 코어의 순수 함수다. **대가는 하나 있다** — ARI로 조율된
  갱신은 CA의 레이트 리밋에서 완전히 면제되는데 우리는 그 면제를 받지
  못한다. 지금은 감당할 만하고, 다시 판단할 조건은 §13에 적어 둔다.
- **비동기 경계**: instant-acme은 async다. ACME 작업은 언제나 tokio
  런타임 안에서 돈다 — `server run`은 이미 런타임이 있고, `server init`
  은 발급 구간에만 런타임을 잠깐 띄운다. HTTP-01 챌린지에 답할 :80
  리스너도 이미 있는 tokio/axum으로 세운다(새 의존성 없음).
- **라이선스**: instant-acme은 Apache-2.0이다(anago는 MIT). 퍼미시브라
  배포에 문제는 없지만 M4의 릴리스 산출물에 NOTICE를 챙겨야 한다.

#### Cloudflare — 새 HTTP 클라이언트를 들이지 않는다

표의 "hyper 직접"을 **기존 `client.rs`(블로킹 rustls 클라이언트) 확장**
으로 확정한다. `join`/`ls`/`rm`이 이미 쓰는 코드이고, 요청 조립과 응답
파싱이 순수 함수로 테스트돼 있다. 남은 일은 임의 호스트·헤더·메서드를
받게 넓히는 것뿐이라 reqwest는 물론 hyper의 클라이언트 API도 새로
배우지 않는다.

DNS-01 흐름은 async 안에 있으므로 Cloudflare 호출은 `spawn_blocking`
으로 부른다. 어댑터가 몇 줄이고, 대신 **anago가 밖으로 내는 HTTP는 한
벌로 유지된다** — 타임아웃·트러스트 루트·에러 문구가 두 군데로 갈라지지
않는 쪽이 유지비가 싸다.

#### 제3자 JSON — `serde_json`을 바이너리에 직접 선언한다

§10.1이 "serde가 다시 논의되는 경우는 하나뿐"이라며 예약해 둔 그
순간이다. 여기서 판단한다: **ACME·Cloudflare 응답은 `serde_json`으로
읽는다.**

왜 코어의 미니 JSON을 쓰지 않는가. 미니 JSON의 엄격함(부동소수 거부,
중복 키 거부, `i64` 하나)은 **우리 스키마에 대해서는** 옳다 — 스키마를
우리가 정하니까 좁혀도 안전하다. 남의 스키마에는 정확히 반대로 작용
한다. Cloudflare 응답의 `meta`처럼 우리가 읽지도 않는 구석에 실수나
스키마 변경이 하나 들어오면 응답 **전체**가 파싱 에러가 되고, A 레코드
upsert가 무관한 이유로 죽는다. 남의 JSON에는 관대한 파서가 맞다.

비용은 사실상 0이다: `serde_json`은 instant-acme 때문에 어차피 트리에
들어온다. 그래도 §7.1의 `sha2`와 같은 이유로 **직접 의존성으로 선언**
한다 — 전이 의존성에 기대어 남의 크레이트를 부르지 않는다.

선은 그대로 유지된다: **우리 타입을 serde로 정의하지 않는다.** 제3자
응답은 `serde_json::Value`에서 필요한 필드만 뽑아 즉시 anago-core의
타입(§8, §9.1)으로 옮긴다. `#[derive(Serialize)]`가 붙은 anago 타입은
M1에도 없다.

#### QR — `qrcodegen`으로 인코딩, 렌더링은 코어의 순수 함수

인코딩은 **`qrcodegen` 1.8**(MIT, 의존성 0)에 맡긴다. 직접 구현하지
않는 이유는 §4 원칙 1과 같다 — 리드-솔로몬·마스킹·버전 선택은 이미 잘
풀린 문제이고, 우리가 다시 풀면 "폰이 스캔을 못 한다"는 형태로만 틀린다.
게다가 그 실패는 유닛 테스트로 잡히지 않고 실기기에서만 드러난다.

대신 **화면에 그리는 일은 anago-core가 한다**: 바이너리가
`qrcodegen`에서 모듈 행렬(불리언)을 받아 넘기면, 코어의 순수 함수가
그것을 터미널 문자열(블록 문자·여백)로 만든다. 크레이트 없이 유닛
테스트되는 표면이 이쪽이고, 이 분리 덕에 QR 출력의 회귀가 `cargo test`
에 걸린다.

코어가 인코더까지 갖는 선택지는 버린다. 순수 std로 못 할 일은 아니지만,
그건 코어를 "우리 규칙을 담는 곳"에서 "우리가 만든 라이브러리를 담는
곳"으로 바꾸는 변경이다 — §4 원칙 4가 코어에 그어 둔 선은 "외부 크레이트
금지"이지 "무엇이든 직접 만든다"가 아니다.

#### DNS-01 전파 확인 — 리졸버는 들이지 않는다

DNS-01 대기는 권한 네임서버에 TXT를 물어야 하는데(§9.1), std에는 이름→
주소 조회만 있고 TXT를 물을 수단이 없다. 선택지는 셋이었다.

- **리졸버 크레이트**(hickory 등): 재귀·캐시·DNSSEC·비동기 런타임까지
  딸려 온다. 우리가 쓰는 것은 그중 질의 하나이고, `qrcodegen`처럼
  "의존성 0짜리 작은 크레이트"가 아니라 스택 하나가 들어온다.
- **`dig` 호출**: 최소 설치 VPS에 `dig`가 없는 경우가 흔하다. 갱신
  시점에 없는 바이너리는 최악의 실패 시점을 고른다.
- **직접 만든다**: 메시지 조립·해독은 순수 계산이고, 픽스처 패킷으로
  전부 유닛 테스트된다. 실제로 그렇게 했다(`anago_core::dnswire`).

QR에서 인코더를 코어에 두지 않기로 한 것과 어긋나 보이지만 갈린 지점은
분명하다. **QR은 틀리면 유닛 테스트에 안 걸리고 실기기에서만 드러나고**,
잘 만들어진 의존성 0짜리 크레이트가 이미 있었다. DNS 쪽은 반대다 —
틀리면 픽스처가 잡고, 대안은 런타임 하나를 끌고 오거나 없을 수도 있는
외부 명령에 기대는 것이다. 그리고 우리가 만든 것은 **리졸버가 아니다**:
재귀도 캐시도 서명 검증도 없고, 이미 권한이 있다고 알려진 서버에 묻고
답을 읽을 뿐이며, 그 답이 틀려도 손해는 검증을 조금 일찍/늦게 넘기는
것뿐이다(진짜 판정은 ACME 서버가 내린다). §4 원칙 1이 위임하라고 한
"어려운 문제"는 이쪽이 아니다.

#### 실제로 들어온 전이 의존성 (측정치)

`instant-acme`를 넣은 뒤 빌드 트리는 **93 → 111개**로 늘었다. 새로 들어온
18개는 다음과 같다:

```
async-trait base64 deranged hyper-rustls instant-acme num-conv pem
powerfmt rcgen rustls-platform-verifier serde_derive thiserror
thiserror-impl time time-core try-lock want yasna
```

**C 툴체인을 새로 요구하는 것은 하나도 없다** — aws-lc-rs를 끈 이유가
이것이다(`cargo tree -i aws-lc-rs` → 없음). 새 크레이트 중 빌드 스크립트가
있는 것은 `thiserror` 하나뿐이고 rustc 버전을 묻는 순수 러스트 프로브다.
`ring`이 `cc`를 빌드 의존성으로 갖지만 그건 M0의 rustls가 이미 데려온
것이라 변화가 아니다. 이 성질은 M4의 "어느 VPS에서나 `cargo build`"를
지키는 조건이므로, 앞으로 의존성을 더할 때마다 같은 확인을 한다.

**anago-core의 의존성은 0개 그대로다**(§4 원칙 4).

#### 암호 백엔드는 feature가 정한다 — 명시적 설치가 아니라

anago의 rustls 호출은 전부 프로바이더를 **명시적으로** 넘긴다
(`builder_with_provider`). 그런데 instant-acme의 기본 HTTP 클라이언트는
rustls의 **암묵적** 기본값을 쓴다. rustls는 그 기본값을 크레이트
feature에서 정하는데, 프로바이더가 정확히 하나 컴파일돼 있으면 그것을
설치하고 **둘이거나 없으면 패닉**한다. anago에 컴파일돼 있는 것은
`ring` 하나뿐이라 그 경로가 안전하다 — 즉 이 안전은 코드가 아니라
**feature 설정이 지키고 있다.** 그래서 `tests/acme_deps.rs`가 그것을
고정한다: ACME 클라이언트를 만든 뒤 설치된 프로바이더의 암호 스위트가
ring의 것과 정확히 같은지 본다. feature 하나가 조용히 aws-lc-rs(그리고
C 툴체인 요구)를 ACME 클라이언트 밑에 밀어 넣는 것이 이 테스트가 막는
실패다.


## 11. 마일스톤

| 단계 | 내용 | 검증 |
|---|---|---|
| M0 | `server init`(DNS는 수동 안내, TLS는 기존 인증서 지정 — 아래 참조) + `join` + 허브-스포크 통신 + `code`/`ls`/`rm` | 실서버: Cloudflare 도메인 + VPS에서 기기 2대 연결, 서로 ping |
| M1 | ACME 자동 TLS + Cloudflare A 레코드/DNS-01 자동화 + `sync` timer + `--export qr` | 폰이 QR로 공식 wg 앱에 합류해 기존 기기와 **상호** ping — 아래 합격 기준 |
| M2 | 홀펀칭 직결: STUN 관측 → /endpoint 보고 → 서버가 중개 → 실패 시 허브 폴백 유지 | LTE↔집공유기 직결 성사율 측정 |
| M3 | 이름 해석(`맥북.net.example.com` 또는 /etc/hosts 갱신), `server status` 대시보드 | |
| M4 | 릴리스: CI + 태그 릴리스 + Homebrew — krill의 워크플로 재활용 | |

**현재 상태(2026-08)**: M0는 **코드가 완성**됐다 — `server init`,
`server run`, `code`, `join`, `ls`, `rm`이 모두 동작하고, 코어는 순수
함수로 유닛 테스트되며 수명주기 시나리오 테스트가 있다. 아직 남은 것은
표의 "검증" 열이다: 실 VPS·도메인·인증서로 기기 2대를 붙여 서로 ping하는
확인은 사람이 해야 하고(§12의 규칙), 항목은 리포지토리 루트의
`HUMAN-VERIFY.md`에 있다. 그 확인이 끝나기 전까지 M0는 "구현 완료,
미검증"이다.

M0의 TLS: 조인 코드가 평문으로 다니면 안 되므로 **TLS는 M0부터 필수**다.
M0에서는 ACME 자동화 없이 "이미 있는 인증서 경로를 지정"(`--tls-cert/key`)
도 받게 해 부트스트랩 문제를 피하고, M1에서 ACME로 자동화한다. 자동화가
수동 경로를 **대체하는 것이 아니라 기본값을 바꾸는 것**이다 —
`--tls-cert/--tls-key`는 M1 이후로도 1급 시민이고(§8), certbot이 이미
도는 서버에서는 그쪽이 옳은 답이다.

### M1의 합격 기준

표의 한 줄이 뜻하는 것을 풀어 둔다. **폰이 붙는 것만으로는 부족하다** —
`--export qr`로 만든 프로필을 공식 wg 앱이 읽어 터널이 서고, 그 폰과
기존 기기가 **양방향으로** ping이 되어야 한다. 한쪽만 되는 것은 허브의
FORWARD 정책 문제이지 M1이 통과한 상태가 아니다(§13).

그 앞에 서야 하는 것들:

- **ACME가 실제로 발급한다.** 스테이징으로 배선을 먼저 확인하고
  (`--acme-staging`), 그다음 `server renew --acme-production`으로 옮긴다.
  이 순서를 권하는 이유는 레이트 리밋이다(§13).
- **A 레코드가 자동으로 선다.** 그리고 그 레코드가 **DNS only**인지
  사람이 눈으로 본다 — 프록시가 켜져 있어도 인증서는 받아지므로
  자동화만으로는 드러나지 않는다(§13).
- **타이머가 실제 주기로 돈다.** 확인 명령을 도메인과 라벨까지 적어
  둔다 — 리눅스는 `systemctl list-timers 'anago-sync*'`, 맥은
  **`sudo launchctl print system/com.github.elpalaiso.anago.sync`**다.
  맥에서 `sudo`와 `system/`이 함께 필요한 이유는 타이머가 사용자
  에이전트가 아니라 시스템 데몬이기 때문이고(§8), 일반 사용자 셸의
  `launchctl list`로는 아예 보이지 않는다.
- **유닛이 가리키는 `device.json`이 맞다.** 위 `print` 출력의
  `ProgramArguments`에서 `--config` 경로를 읽어 **가입한 사용자의**
  파일인지 확인한다(리눅스는 `systemctl cat anago-sync.service`의
  `ExecStart`). root의 `/root/.config/...`를 가리키고 있으면 그 타이머는
  영영 아무것도 못 한다 — §8이 경로를 유닛에 굽는 이유가 이것이다.
- **재부팅 후에도 셋이 살아 있다.**

**갱신은 실제 갱신 시점까지 기다려 확인할 수 없다**(인증서 수명이
얼마든 몇 주 단위다 — §13). 두 갈래로 나눠 본다: 재발급
경로 자체는 `server renew --force`로 태우고, **주기 점검이 실제로
트리거되는지**는 상태의 `renew_after`를 과거로 손수 당겨 확인한다.
§9.1이 만료가 아니라 **결정**을 파일에 적기로 한 덕에 이 확인이 가능하다
— 사람이 열어 날짜를 바꿀 수 있는 값이라서다.

이 확인들은 전부 사람 몫이고(§12), 항목은 `HUMAN-VERIFY.md`에 M1 절로
들어간다.

**Cloudflare origin cert의 단서**: M0의 기기는 서버에 직접 붙고, 검증은
기기의 OS 신뢰 저장소로 한다. origin cert는 공개 신뢰가 아니므로 그대로
쓰면 `join`이 `UnknownIssuer`로 실패한다 — 쓰려면 합류하는 모든 기기에
Origin CA를 설치해야 한다. 기본 경로는 공개 신뢰 인증서(Let's Encrypt 등)
이고, origin cert가 1급 시민이 되는 것은 Cloudflare를 앞단에 두는 구성이
생길 때다.

**실검증 환경**: 소유자의 개인 도메인(Cloudflare 등록) + VPS. 따라서
Cloudflare 경로(A 레코드 자동화, DNS-01, origin cert)가 1차 시민이고
모든 마일스톤의 실기기 검증은 이 환경에서 한다.

## 12. 개발 방식 — krill로 만든다 (dogfood)

이 프로젝트는 **krill의 협업 모드로 개발한다**: 마일스톤을 `krill plan`
으로 분해·승인하고, 작업 슬라이스는 `krill duet`(worker + reviewer 교차
모델, gate = `cargo test`)으로 구현한다. 도구로 도구를 만들었던 krill의
부트스트래핑을 한 단계 확장하는 실험이자, krill §12(협업 모드)의 실전
검증장이다. 발견되는 krill의 문제는 krill 리포의 백로그로 환류한다.

에이전트 작업 규칙(CLAUDE.md에도 요약):
- 작업 전 이 문서를 읽는다. 설계 변경은 문서 갱신이 먼저다.
- anago-core는 순수 std 유지, env를 바꾸는 테스트 금지(씸 패턴 — krill
  CLAUDE.md의 규칙과 동일).
- 실서버가 필요한 검증은 에이전트가 하지 않는다 — 모킹 대신 순수 함수
  분리로 테스트하고, 실기기 검증 항목은 PR 본문에 "사람 확인 필요"로
  명시한다.

## 13. 리스크와 열린 질문

- **wg-quick 의존의 플랫폼 편차**: 맥은 wireguard-tools(brew), 리눅스는
  배포판 패키지. 설치 확인·안내를 join이 해준다. Windows는 v1 비대상
  (WSL2 안내).
- **VPS 방화벽/보안그룹**: :443(API)·:51820/udp(wg)·(HTTP-01이면 :80)을
  열어야 한다. init이 감지는 못 하니 체크리스트로 안내하고, 연결 실패
  시 진단 메시지(`anago server status`가 포트 리스닝 확인)를 준다.
  인바운드만으로는 부족하다: 기기 간 패킷은 허브를 **경유**하므로 호스트
  방화벽의 FORWARD 정책도 `anago`→`anago`를 허용해야 한다. UFW처럼
  라우팅 기본값이 거부인 구성에서 "허브에는 닿는데 기기끼리는 안 닿는"
  증상이 나오는 흔한 원인이고, anago는 wg 설정에 `PostUp` 규칙을 넣지
  않으므로(설정 파일이 곧 상태라는 성질을 지키려고) 운영자 몫이다.
- **Cloudflare 프록시**: A 레코드가 프록시(주황 구름)면 이름이 Cloudflare
  주소로 해석되고 `51820/udp`는 전달되지 않는다. 기기는 서버에 직접
  붙으므로 **DNS only**여야 한다. §11의 실검증 환경이 Cloudflare 도메인
  이라 특히 밟기 쉽다.
  - **M1에서 이 함정이 더 고약해진다.** 프록시가 켜져 있어도 **인증서는
    받아진다** — HTTP-01은 Cloudflare가 :80을 오리진으로 넘겨 주니 통과
    하고, DNS-01의 TXT 레코드는 애초에 프록시 대상이 아니다. 그래서
    자동화가 전부 성공하고 로그도 초록인데 **터널만 죽어 있는** 상태가
    만들어진다. 자동화가 늘어날수록 사람이 이걸 눈치챌 계기가 줄어든다.
  - 그래서 anago는 레코드를 **만들 때** `proxied=false`로 만들고, **이미
    프록시가 켜진 레코드는 끄지 않고 거부한다**(§9.1). 끄지 않는 이유는
    그 도메인을 프록시 뒤에 두고 쓰는 사람이 있을 수 있어서다 — 남의
    트래픽 경로를 말없이 바꾸는 것은 anago의 범위가 아니다. 사람이 고칠
    일이라고 말하고 멈춘다.
- **HTTP-01과 DNS-01의 맞바꿈(M1)**: 둘은 편의와 폭발 반경을 맞바꾼다.
  - **HTTP-01**은 :80을 열어야 한다. 방화벽 항목이 하나 늘고(클라우드
    보안그룹과 호스트 양쪽), 이미 :80을 쓰는 웹서버가 있으면 발급 순간
    포트를 잡지 못해 실패한다. 대신 서버에 남는 비밀이 없다.
  - **DNS-01**은 :80이 필요 없다. 대신 **zone DNS 편집 권한을 가진 토큰이
    VPS에 상주한다** — 갱신 때마다 필요하므로 파일로 남을 수밖에 없다
    (§9.1). 서버가 털리면 그 토큰으로 **그 도메인 전체의 레코드**를 바꿀
    수 있다. anago가 다루는 다른 어떤 비밀보다 반경이 크다(wg 개인키는
    그 터널 하나, 기기 토큰은 그 기기 하나다). 토큰 스코프를 해당 zone의
    DNS 편집으로 좁히는 것은 필수이고, 그래도 반경은 "그 도메인 전체"다.
  - **열린 질문**: §11이 정한 기본은 "토큰이 있으면 DNS-01"인데, 그러면
    **A 레코드 자동화를 원했을 뿐인 사람이 상주 비밀을 하나 얻는다.**
    토큰을 init에서만 쓰고 잊는 길(HTTP-01)이 있는데도 그렇다 — §9.1이
    "없앨 수 있는 비밀은 없앤다"고 해 놓고 기본값이 그것을 버리는 셈이다.
    M1에서 마일스톤 정의를 뒤집지는 않되(탈출구는 `--acme-challenge`로
    이미 있다, §8) 실검증에서 두 경로를 다 태워 보고 M2 전에 다시
    판단한다.
- **Let's Encrypt 레이트 리밋(M1)**: 한도는 **토큰 버킷**이라 시간이
  지나면 여력이 점진적으로 다시 찬다. "걸리면 일주일 정지"가 아니라
  "언제부터 다시 되는지"의 문제이고, 그 시각은 **레이트 리밋 응답의
  `Retry-After` 헤더가 알려 준다.**
  - **anago는 그 헤더를 따른다.** 자기 백오프로 덮어쓰지 않고, 헤더가
    있으면 그 시각 전에는 재시도하지 않으며, 사람에게도 그 시각을 그대로
    말한다. CA가 아는 것을 우리가 다시 추측할 이유가 없다.
  - **정상 갱신은 대부분의 한도에서 면제된다.** 이름 조합(identifier set)
    이 같은 갱신은 계정별 신규 주문·도메인별 신규 인증서 한도에 걸리지
    않는다. 그래도 anago에 남는 위험은 둘이다:
    1. **같은 이름 조합의 중복 인증서 한도** — `renew --force`를 반복하면
       여기 걸린다. `--force`에 경고를 붙이는 이유다(§8).
    2. **인증 증명 실패 한도** — 배선이 틀린 채로(:80이 막혔거나 TXT가
       안 서거나) 재시도를 반복하면 여기 걸린다. **셋업 중에 훨씬 흔한
       쪽이 이것이다.**
  - 그래서 **첫 셋업과 배선 확인은 `--acme-staging`으로** 한다. 스테이징의
    한도는 훨씬 넉넉하고, 그 인증서가 공개 신뢰가 아니라 `join`이
    `UnknownIssuer`로 실패하는 것은 **정상이다** — 그 단계에서 보는 것은
    :80/DNS/포트 배선이지 신뢰가 아니다. 확인되면
    `server renew --acme-production`(§8).
  - **ARI를 켜면 갱신이 한도에서 완전히 면제된다.** §10.2는 파서 십수 개를
    피하려고 ARI를 껐고, 그 대가가 이것이다. 지금은 감당할 만하지만
    수명이 짧아질수록 갱신 빈도가 배로 늘므로, **M2 이후에 다시 판단할
    항목으로 남긴다.**
  - 구체적인 숫자는 CA가 바꾸므로 이 문서에 박지 않는다. 규칙만 적는다:
    `Retry-After`를 따르고, 실패한 채로 두들기지 않는다.
- **인증서 수명 단축(M1~)**: Let's Encrypt는 기본 수명을 90일에서 64일,
  다시 45일로 줄이는 전환을 공지했다. anago에 주는 영향은 셋이다.
  - **고정 일수 갱신 규칙은 쓸 수 없다.** §9.1의 `renew_after`가 고정
    일수가 아니라 **수명의 2/3**인 이유가 이것이다. 그래서 `not_after`가
    장식이 아니라 계산의 입력이고, 그것을 못 읽었을 때의 폴백은 가장 짧은
    수명을 가정한다.
  - **갱신 빈도가 오른다.** 데몬의 주기 점검과 실패 재시도가 그만큼 자주
    돌고, 위 항목의 한도 계산도 함께 조여진다.
  - **전환은 진행 중이다.** 이 문서가 특정 일수를 근거로 삼지 않는 것이
    중요하다 — 수명을 묻는 곳은 인증서 자신(`not_after`) 하나여야 한다.
- **맥의 launchd 권한 차이(M1)**: sync는 wg 설정을 적용하므로 root여야
  하고, 그래서 맥에서도 사용자 LaunchAgent가 아니라
  `/Library/LaunchDaemons`의 데몬이다(§8). 여기서 리눅스와 갈린다.
  - 최신 맥OS는 백그라운드 항목을 시스템 설정에 노출하고 **사람이 끌 수
    있다.** "설치는 됐는데 안 돈다"의 흔한 원인이라 설치 출력이 확인
    방법을 함께 안내해야 한다.
  - 데몬이 사용자 홈의 `device.json`을 읽는다. `~/.config`는 TCC 보호
    대상이 아니지만, `XDG_CONFIG_HOME`을 `~/Documents` 같은 보호 폴더로
    옮겨 둔 경우 root 데몬이 읽지 못할 수 있다 — 실기기에서 확인할
    항목이다.
  - 맥의 wg는 유저스페이스(wireguard-go)라 인터페이스 이름이 `utun*`으로
    잡힐 수 있어, `wg syncconf`가 가리킬 이름이 리눅스와 다를 수 있다.
    M0의 `wg-quick` 편차(위 첫 항목)와 같은 뿌리이고, sync가 그 이름을
    어떻게 찾는지가 M1에서 처음 문제가 된다.
- **홀펀칭 성사율(M2)**: 대칭 NAT/CGNAT에서 실패가 정상. 폴백이 기본
  경로라 기능 저하일 뿐 장애가 아니다 — 측정해서 문서에 싣는다.
- **서버 상태 파일 단일화**: 동시 join은 드물지만 파일 락(flock)으로
  직렬화한다. 락은 `state.json`이 아니라 옆의 `state.lock`에 건다 —
  상태 파일은 tmp+rename으로 교체되므로 그 자체를 잠그면 각 writer가
  서로 다른 inode(하나는 이미 unlink된)를 잠그게 되어 직렬화가 무너진다.
- **이름(anago) 충돌**: crates.io 확인 필요(프록시로 미확인). 바이너리
  이름과 크레이트 이름은 분리 가능하므로 블로커 아님.
